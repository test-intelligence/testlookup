# Compliance & governance

For regulated teams, "we shipped it" isn't enough — you need to show *why it was safe to ship*, with evidence, after the fact. A **compliance pack** is TestLookup's answer: a point-in-time, exportable snapshot of everything behind a release decision, assembled in one action and stored durably.

> Compliance packs are an **enterprise feature** behind the `release_compliance_pack` flag. If the controls below aren't visible, an admin needs to enable the flag ([Administration → Feature Flags](administration.md#operating-the-instance)); the API returns 503 when it's off.

## What's in a pack

Generating a pack for a release captures, as of that moment:

- **The release & its decision** — the run, the GO / CONDITIONAL_GO / NO_GO verdict, and the evidence behind it (see [Release gates](release-gates.md)).
- **The policy snapshot** — the exact thresholds, weights, rules, and bands the verdict was computed against (not today's policy — the one in force then).
- **The decision trail** — the sequence of steps and decisions that produced the verdict, including any human override and its recorded reason.
- **Failure clusters** — what was failing and how it grouped.
- **Defects** — the tracked bugs linked to the release.
- **Audit events** — the who-did-what around the release (overrides, quarantine decisions, admin actions).

The pack is self-contained and reproducible: because the policy and decision are snapshotted, a pack means the same thing a year later even if your policies have changed since.

## Generating and downloading a pack

From a release (**Releases** → the release, where the compliance-pack panel lives):

1. Generate the pack for the release.
2. It's assembled server-side and stored durably (object storage), so it survives UI and data changes.
3. Download it for your audit trail / release record.

The same is available programmatically — the MCP server exposes `list_compliance_packs` and `generate_compliance_pack`, so an assistant or pipeline can produce the evidence bundle without clicking through the UI ([CLI, SDKs & MCP](cli-sdk-mcp.md#the-mcp-server)).

## Resilience by design

Pack assembly is deliberately fault-tolerant: the decision-trail and audit-event sections **self-guard** — if one can't be gathered, it embeds an error note in the pack rather than failing the whole generation. You get the pack you can get, with gaps marked, instead of nothing.

## The governance surround

A compliance pack draws on systems documented elsewhere:

- **Audit Dashboard** (`/settings/audit`) — the live who-did-what the pack snapshots ([Administration](administration.md#operating-the-instance)).
- **Decision Trail** — the per-decision provenance also visible in the AI surfaces ([AI features](ai-features.md)).
- **Release Gate & policies** — the verdict and the policy it was judged by ([Release gates](release-gates.md)).

## When to generate one

- **At each release decision** — especially any CONDITIONAL_GO or overridden verdict, where "why did we ship anyway?" is the question an auditor will ask.
- **Before a policy change** — a pack freezes the old policy's evidence for releases already judged under it.
- **On request** — audit, incident review, or a customer's compliance ask.

### How a pack proves it hasn't been altered

Each pack ships a `manifest.json` holding a SHA-256 digest of every other file in the ZIP, and the digest of that manifest is stored on the `compliance_packs` row (`manifest_sha256`). Re-hash the manifest, compare it to the row, then re-hash each file against the manifest, and any edit anywhere in the pack shows up. The pack's own README spells out the three steps.

Call this what it is: **tamper-evidence, not a signature.** There is no HMAC or PKI signing over the pack, so the chain detects accidental corruption and after-the-fact edits to the object in storage — it does not defeat an attacker who can rewrite both the stored ZIP *and* the database row. If you need non-repudiation, sign or timestamp the downloaded pack with your own key management, or copy it to WORM/object-lock storage on download.

## Control-family mapping

TestLookup is **not certified** against SOC 2, GDPR, HIPAA, or any other framework, and nothing here claims the product "meets" or "complies with" a standard. Certification attaches to an organisation and how it operates, never to a piece of software. What follows is an **enablement mapping**: for each control family an auditor is likely to raise, it states what the product actually gives you, points at the exact surface where that evidence lives, and names the limits. Your policies, your hosting environment, and your operating discipline complete every row.

Read each row as: *the control is yours — here is the part of it TestLookup can evidence.*

Every "Where to see it" cell is a concrete pointer — a UI path, an API endpoint, a table name, or a source file — that you or your auditor can open and check for yourself. Where a capability is thinner than the control family implies, the limits column says so inline rather than hiding it in a footnote. A mapping that over-claims is worse than no mapping.

Three facts apply to almost every row and are stated once here instead of repeated:

- **TestLookup is self-hosted.** You run the containers on infrastructure you control. There is no vendor-operated service holding your data, which removes a large class of sub-processor and cross-border questions — and moves the corresponding controls onto you.
- **The product is data-processing software, not a management system.** It produces evidence; it does not run your access-review cadence, your risk assessment, or your incident process.
- **Defaults are the conservative ones.** Offline mode on, retention purge off, compliance packs behind a flag, dev conveniences disabled. Anything you turn on is a decision you should be able to point at.

## What TestLookup does NOT provide

This is the section that makes the rest of the document worth reading. If a control you need is here, plan for it elsewhere — do not let a mapping table imply otherwise.

- **No certification and no attestation.** There is no SOC 2 report, no ISO certificate, no HITRUST, and no third-party audit of the product. Every claim above is a pointer to source you can read, which is the only kind of assurance an unaudited self-hosted product can honestly offer.
- **No BAA and no DPA with a vendor.** In a self-hosted deployment nobody else processes your data, so there is no counterparty to sign one — which also means there is no one to escalate to.
- **Bulk data at rest is not encrypted by the application.** Only secrets are (Fernet, from `APP_SECRET_KEY`). PostgreSQL, MongoDB, and MinIO/S3 contents — test data, failure text, analyses, reports, audit rows — are written in the clear as far as the app is concerned. Encrypting them is delegated to your storage or platform layer (encrypted volumes, transparent database encryption, S3 SSE) and **you must configure it**; nothing in the product will warn you if you don't.
- **TLS and in-transit protection are inherited from the deployment target.** The application serves plain HTTP behind your ingress. The OpenShift overlay uses Routes with edge TLS; other overlays depend on whatever you put in front. There is **no in-cluster mTLS** between services and datastores.
- **No MFA, no account lockout, no password complexity or rotation policy.** Length (8 characters) is the only password rule. Bring these from your IdP over SAML.
- **No subject-level data access or erasure workflow.** Retention and reset operate on projects and time windows. There is no "export everything about this person" and no "delete this person"; user accounts deactivate rather than delete, and `DELETE /api/v1/projects/{id}` is a soft delete that removes no data.
- **Audit immutability is a convention, not an enforced constraint.** No database triggers, restricted grants, WORM storage, or hash-chaining protect the audit tables from direct database modification.
- **Compliance packs are tamper-evident, not signed.** No HMAC, no PKI, no trusted timestamp.
- **No physical safeguards.** Facility access, workstation security, device and media controls, and media disposal all belong to whoever hosts the containers.
- **No incident response, breach notification, or alerting features.** The audit dashboard is query-and-export only, with no rules, thresholds, or notifications on audit events, and no SIEM forwarder.
- **Backup and DR are only partly shipped.** `make backup` / `make restore` / `make preflight` / `make upgrade` are real, documented, and tested, but they drive **Docker Compose only** — the Kubernetes overlays are not covered. Nothing schedules a backup, copies it off-host, encrypts it, expires it, or verifies a restore. No RTO or RPO is defined. See [Backup, restore & upgrades](administration.md#backup-restore--upgrades).
- **No access-review, recertification, or segregation-of-duties workflow.** The data to run a review exists; the cadence and the sign-off do not.
- **Redaction is best-effort.** Key-name and regex matching over free text. It will miss PII in unanticipated shapes and will sometimes redact things you wanted to keep. Do not treat it as a de-identification control, and certainly not as HIPAA de-identification under §164.514.
- **Tenancy isolation is logical, not physical.** One database, project-scoped queries, per-project caches and vector collections. No per-tenant database and no per-tenant encryption key.

## Evidence-gathering quickstart

When an auditor asks a question, this is the surface that answers it. Start here rather than in the database.

| The question | Where the answer lives | How to pull it |
|---|---|---|
| "Show me who could access this project and how that changed." | Audit dashboard, `access` category | `/settings/audit` filtered to access, or `GET /api/v1/audit-dashboard/events?category=access&project_id=…`. For one person, `GET /api/v1/users/{id}/access-audit`. |
| "Prove this release was authorised, and against what criteria." | Compliance pack | Generate one from the release (`POST /api/v1/releases/{id}/compliance-pack`), then download it. It contains the decision, the policy **as it stood then**, the decision trail, any override and its reason, failure clusters, linked defects, and the surrounding audit events. See [What's in a pack](#whats-in-a-pack). |
| "Prove that pack hasn't been altered since." | `compliance_packs.manifest_sha256` | Re-hash `manifest.json` and compare to the row, then re-hash each file against the manifest. The pack's README has the steps. Tamper-evidence only — see the caveat above. |
| "Show your data-retention practice and prove it runs." | Retention policy + purge audit | `/settings/retention` for the four windows and the enabled flag; `POST …/retention-policy/preview` for a dry run showing exactly what would be removed today; the `last_purge` record on the policy GET, or `settings_audit_log` under `retention_purge:<project_id>` for cutoffs, per-store deletion counts, duration, and errors. |
| "Who changed configuration or rotated a credential?" | `settings_audit_log` | Audit dashboard, `settings` category. Records the setting key, the action, the actor, and **field names only** — never secret values. |
| "Show authentication and provisioning activity, including failures." | `identity_events` | `GET /api/v1/identity/events`, or the events view on `/settings/sso`. Covers SSO logins and failures, SCIM create/update/deactivate/reactivate, sync errors, JIT provisioning, role mapping, and admin fallback logins — with IP and error detail. |
| "Show that changes to test content were tracked." | `test_case_audit_logs` | Audit dashboard, `test_management` category — entity, action, actor, and old/new values for test cases, plans, strategies, and reviews. |
| "Give me an offline evidence file for the whole window." | Audit CSV export | `GET /api/v1/audit-dashboard/export?days=…&category=…` (ADMIN, up to 365 days per call, redaction applied). |
| "Prove no data left the environment." | Offline-mode configuration | Show `AI_OFFLINE_MODE` in the deployed environment and the gate sites listed under CC6.6, plus the effective AI configuration at `/settings/ai`. Pair it with network egress evidence from your own infrastructure — the application can show its own posture, not your network's. |
| "Show that these security properties can't silently regress." | CI gates | `scripts/quality_gate.py` and `backend/tests/test_architectural_authorization.py` run on every merge; see [DEVELOPER_GUIDE.md](../architecture/DEVELOPER_GUIDE.md) for the full gate list. |

For the architectural view behind these surfaces — identity, the authorization guard family, tenancy, and what enforces them — see [SECURITY.md](../architecture/SECURITY.md).
