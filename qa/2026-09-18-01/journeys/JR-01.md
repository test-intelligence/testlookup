## Happy path — `POST /api/v1/ingest/file`

A JWT is accepted on the ingest endpoint (it is not API-key-only), which is
worth knowing: the surface has two authentication paths onto the same data, and
EX-05 should exercise both.

```
POST /api/v1/ingest/file   (multipart: file, project_id, build_number)
 -> 202 {"status":"accepted","run_id":"…","task_id":"…","total_results":0}

GET /api/v1/ingest/uploads/{task_id}
 -> {"state":"succeeded",
     "result":{"total":6,"attempted":6,"rejected":0,"complete":true,
               "passed":3,"failed":2,"skipped":1,"broken":0,"unknown":0}}
```

Every count matches the file. `total_results: 0` in the 202 is correct and not a
defect — the count is unknown until the async parse runs, and the endpoint's own
docstring says so.

### What the run row carried

| Field | Value | Verdict |
|---|---|---|
| `total_tests` / `passed` / `failed` / `skipped` | 6 / 3 / 2 / 1 | correct |
| `pass_rate` | 60.0 | correct — skipped excluded from the denominator |
| `primary_suite_name` | `AuthSuite` | correct, **not NULL** |
| `suite_names` | 1 entry | correct |
| `ingestion_complete` / `rejected` | `True` / 0 | correct |
| `status` | `FAILED` | correct |
| `minio_prefix` | `uploads/<project>/<run>/` | artifact stored |
| `run_seq` | 1 | correct |
| `duration_ms` | **`None`** | **DEFECT — TL-2026-09-18-01-005** |

Per-case durations were all stored correctly (1234, 892, 2100, 3210, 4120, 900 —
summing to 12456 ms, exactly the suite's declared `time="12.456"`), so the data
arrived intact and was dropped only at the run aggregate. Fixed; see the defect
file. Re-ingesting the same file after the fix produced `duration_ms = 12456`.

Suite-name NULLs and suite clobber — both prior defect classes in this repo —
did **not** reproduce on this path.

## Error paths

| Input | Sync response | Async task state | Orphan run? |
|---|---|---|---|
| 0-byte file | `400 {"detail":"Uploaded file is empty"}` | n/a | none |
| Truncated XML (one `<testcase>`, no closing tag) | `202 accepted` | `failed`, `{"code":"empty_report","message":"No test results were found in the file. Check that the format matches the file contents."}` | **none — `GET /runs/{id}` → 404** |
| Not XML at all (`not xml at all`) | `202 accepted` | `failed`, same coded error | **none — 404** |
| `project_id` not a UUID | `400 "Invalid project_id — expected a UUID"` | n/a | none |

This is the behaviour the mission asked for: a rejected upload produces an
actionable error and **no partial run**. The async 202 is correct for a queued
parse, and the failure is coded (`empty_report`) rather than free text, so a CI
client can branch on it.

**One observation, not filed as a defect.** The truncated file was not empty —
it contained one well-formed `<testcase>` before the truncation — and is
diagnosed as `empty_report`. The message does point at format-versus-contents,
which is actionable, but "no results found" and "this file is cut off" are
different problems for a user chasing a broken CI artifact. Recording it here
rather than filing it: the behaviour is defensible and the wording is a
judgement call, not a fault.
