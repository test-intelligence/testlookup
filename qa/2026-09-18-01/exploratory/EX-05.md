# EX-05 — Authorization: 5 roles, server-side

- Agent: ORCH (acting as EX)
- Environment: LOCAL (`make dev`), backend `:8000`
- Charter: for each of `VIEWER, TESTER, QA_ENGINEER, QA_LEAD, ADMIN`, attempt
  management surfaces **directly against the API**, bypassing the SPA.
  `ManagementGuard` in `App.tsx` is a client-side redirect and proves nothing.
- Status: partial — result below is trustworthy for what it covers, and what it
  does not cover is named.

## Result: server-side authorization holds on every endpoint tested

**No defect found.** Recorded in full because a negative result here is worth as
much as a finding, and because the first version of this matrix was wrong.

### Reads

| Endpoint | ADMIN | QA_LEAD | QA_ENGINEER | TESTER | VIEWER |
|---|---|---|---|---|---|
| `GET /api/v1/users?limit=1` | 200 | 200 | **403** | **403** | **403** |
| `GET /api/v1/users/{id}` | 200 | 200 | **403** | **403** | **403** |
| `GET /api/v1/feature-flags` | 200 | **403** | **403** | **403** | **403** |
| `GET /api/v1/projects?limit=1` | 200 | 200 | 200 | 200 | 200 |
| `GET /api/v1/runs?limit=1` | 200 | 200 | 200 | 200 | 200 |

`/users` matches its declared `Depends(require_role(UserRole.QA_LEAD))` and its
docstring ("Requires QA_LEAD or higher"). `/projects` and `/runs` are readable
by every authenticated role, which is the intended product behaviour — they are
the app's primary read surfaces.

### Writes

| Attempt | ADMIN | QA_LEAD | QA_ENGINEER | TESTER | VIEWER |
|---|---|---|---|---|---|
| `PATCH /users/{id}/role` | 200 | **403** | **403** | 400 † | **403** |
| `PATCH /users/{id}/status` | 200 | **403** | **403** | **403** | **403** |
| `POST /projects` | 201 | 409 ‡ | **403** | **403** | **403** |

† **Not an anomaly — my matrix contaminated itself.** The loop ran ADMIN first,
and ADMIN's `PATCH .../role` to `ADMIN` *succeeded* against the tester account.
Roles are resolved from the database per request, so by the time the TESTER row
ran, that account really was an ADMIN; it cleared `require_role(ADMIN)` and hit
the handler's own "cannot change your own role" guard, which answers 400.
Sequential mutations inside a role matrix poison the later rows. Recorded so the
400 is not read as an inconsistent guard.

‡ 409 is a duplicate-slug conflict, not a refusal — QA_LEAD **is** permitted to
create projects, and ADMIN had already created that slug one row earlier. Same
self-contamination.

## The instrument was broken first, and that is the main lesson here

The first run of this matrix reported **200 for every role on every endpoint**,
including `/users` for VIEWER — which reads as a severe authorization breach and
would have been filed as S1.

It was wrong. `POST /api/v1/auth/dev-login` declares

```python
async def dev_login(role: str = "admin", username: str | None = None, ...)
```

Bare scalars in FastAPI are **query** parameters. I was sending
`{"username": "viewer"}` as a JSON body, which the endpoint ignored entirely, so
every call fell through to the default `role="admin"`.

The tell was cheap and decisive: every token's `sub` claim was the same UUID, and
`GET /api/v1/auth/me` returned `admin / ADMIN` for all five. **Five tokens, one
identity — the matrix measured admin five times.**

Correct usage is `POST /api/v1/auth/dev-login?username=viewer`, after which
`/auth/me` returns a distinct identity per role and the table above appears.

This is not a product defect. `dev-login` is environment-gated, 404 in
production, and even restricts its `username` path to synthetic
`@testlookup.dev` accounts so it cannot impersonate a real one. It behaved
exactly as written; the probe was wrong.

**Check the identity behind the token before trusting any authorization
matrix.** An authz test that silently runs as one principal reports "no
difference between roles" as either a total breach or a total pass, and both
readings are fiction.

## Live-mutation cleanup

This mission wrote to the local stack and reverted everything:

- `tester` role restored `ADMIN` → `TESTER` (verified: all five seeded users
  back to their original roles).
- Project `exj-authz-probe` deleted (`204`; verified absent from `/projects`).

One leftover was checked and is **correct behaviour, not a defect**: deleting
the project left its auto-provisioned synthetic QA lead `qalead-exj-authz-probe`
as a row, but with `is_active = false` and zero memberships. Deactivating rather
than deleting preserves ownership references and the audit trail. Filed here as
a verified negative so the next person who spots the row does not re-open it.

## Not covered — `measured: false`

- Ids arriving via **query params, request bodies and headers** rather than the
  path. This is the highest-value part of the charter and is not done: nine
  IDORs have previously hidden in exactly that shape.
- The remaining ~26 management routes' endpoints. Five were probed; the URLs for
  several others were guessed and returned 404, so they must be taken from the
  OpenAPI document rather than invented.
- API-key authentication as a second path onto the same data. JR-01 established
  that `POST /api/v1/ingest/file` accepts a **JWT**, so there are two
  authentication paths onto ingestion and only one was exercised.
- Cross-project authorization — that is EX-06 and is not started.
