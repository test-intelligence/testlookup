# EX-06 — Tenancy: cross-project leak hunt

- Agent: ORCH (acting as EX)
- Environment: LOCAL (`make dev`)
- Charter: with two projects seeded, attempt to read project B's data while
  scoped to project A — including ids arriving via **query parameters**, which
  is where nine IDORs have previously hidden in this codebase.
- Risk: **R1**, the top-ranked risk in the plan.
- Status: partial — no leak found on the surfaces tested; each negative carries
  the control that makes it worth reading.

## Setting up a subject that can actually leak

All five seeded users are members of all three seeded projects, so none of them
can demonstrate isolation. A fourth project was created for this mission:

- `EXJ Tenancy B` (`exj-tenancy-b`), members: `admin` and the auto-provisioned
  synthetic `qalead-exj-tenancy-b`. `qa_lead`, `qa_engineer`, `tester` and
  `viewer` are **not** members.
- `samples/junit/payment-suite.xml` ingested into it — 8 tests, `PaymentSuite`,
  `duration_ms = 28730` (a second confirmation of the TL-2026-09-18-01-005 fix,
  on a different file).

## Result: no cross-project leak on any surface tested

| Request (project B, as a non-member) | ADMIN | QA_LEAD | QA_ENG | TESTER | VIEWER |
|---|---|---|---|---|---|
| `GET /projects/{B}` | 200 | 403 | 403 | 403 | 403 |
| `GET /runs/{runB}` | 200 | 404 | 404 | 403 | 404 |
| `GET /runs/{runB}/tests` | 200 | 404 | 404 | 403 | 404 |
| `GET /runs?project_id={B}` | 200 | 403 | 403 | 403 | 403 |
| `GET /suites?project_id={B}` | 200 | 403 | 403 | 403 | 403 |
| `GET /search?q=…&project_id={B}` | 200 | — | — | — | 403 `"You do not have access to this project"` |
| `GET /test-management/cases?project_id={B}` | 200 | — | — | — | 403 same |
| `GET /metrics/summary?project_id={B}` | 200 | 200 | 200 | 403 | **200** |

The query-param path — the shape that has hidden IDORs here before — refuses
correctly on `/runs`, `/suites`, `/search` and `/test-management/cases`.

### The one 200 that had to be opened, not counted

`GET /metrics/summary?project_id={B}` answers **200 to three non-members**. On
the status code alone that reads as a leak. It is not:

```
ADMIN  (member)     -> {"total_executions_7d":{"value":8}, "avg_pass_rate_7d":{"value":75.0},
                        "new_failures_24h":{"value":2}, "avg_duration_ms":{"value":28730}, …}
VIEWER (non-member) -> {}
```

An empty object. No figure from project B crosses. The endpoint is inconsistent
in *shape* with its neighbours — `200 {}` where `/runs` and `/suites` return
403 — but it is not inconsistent in *substance*, and `{}` arguably confirms less
about whether the project exists than a 403 does. Recorded as an observation,
not filed: nothing leaks, and the quieter refusal is defensible.

This is why the charter says to read the body. A status-code-only sweep would
have filed an S1 here.

### The negative that needed a positive control

Unscoped search — `GET /search?q=PaymentSuite&limit=50`, no `project_id` — is
200 for a VIEWER, and returned **0** items belonging to project B.

Zero is only evidence if the probe could have seen a leak. `project_id` is not
in the search response payload, so the check was made on `test_run_id`, and the
control was run:

```
VIEWER unscoped search -> 20 results, 0 of them the project-B run
ADMIN  unscoped search -> 20 results, 8 of them the project-B run   <- CONTROL PASSES
```

Admin's identical query finds the B run eight times over, so the index holds it
and the viewer's zero is a filter doing its job — not an empty index, and not a
query that matched nothing. Without that control, "0 leaked items" would have
been indistinguishable from a probe that was blind.

## Live-mutation cleanup, and a second verified negative

Project B deleted (`204`; absent from `/projects`).

Deletion is a **soft** delete (`routers/projects.py:260` names it), and its run
remains readable by direct id to an ADMIN. Checked rather than assumed:

| After deletion | Result |
|---|---|
| Run present in `GET /runs?limit=100` | **No** — excluded from listings |
| `GET /runs/{runB}` as non-member VIEWER | **404** |
| `GET /runs/{runB}` as ADMIN with the exact id | 200 |

That is a coherent soft-delete: gone from every listing, invisible to anyone
without access, still addressable by an administrator who knows the id. It
matches the repo's existing `exclude_deleted_projects` regression family
(`test_analytics_exclude_deleted_projects`,
`test_canonical_cases_exclude_deleted_projects`). Filed as a verified negative
so the next person who notices the 200 does not re-open it.

The synthetic `qalead-exj-tenancy-b` remains as a deactivated row, same as in
EX-05 — `is_active=false`, no memberships.

## Not covered — `measured: false`

- Ids in **request bodies and headers**. Only path and query-param shapes were
  exercised; the charter asks for all three.
- Write paths across tenants — can a non-member *modify* project B's data? Only
  reads were probed.
- Activity, audit and notification surfaces (`/api/v1/activity?project_id=…`
  answered 404 for admin too, so the path is wrong and must be taken from the
  OpenAPI document rather than guessed).
- Search **facets and counts**, as distinct from search results. A facet that
  counts across tenants leaks existence without leaking rows.
- API-key authentication as a second path onto the same data.
