# TL-2026-09-18-01-007 — `/intelligence` "Recent runs analyzed": Build eats the width, the other columns clip

- Reported by: **user**, with a screenshot of `http://testlookup.local/intelligence`
- Confirmed by: source inspection of the column budget, which states the single
  viewport it was measured at
- Severity: S2 (data a user came to read is not readable)
- Priority: P1
- Component/surface: `frontend/src/pages/IntelligenceHubPage.tsx:725-742`,
  the "Recent runs analyzed" table
- Journey: JR-04 (AI report) — adjacent surface
- Status: **BACKLOG** — filed, not fixed in this program

## Reproduction

1. Open `http://testlookup.local/intelligence` on a wide display (the reported
   screenshot is ~2000px; the table's own budget was tuned at 1345px).
2. Read the "Recent runs analyzed" table.

Expected: every column shows its value.

Observed, from the reported screenshot:

- **Build** occupies a very large, mostly empty band — the run label sits at the
  far left and the rest is blank.
- **Suite** shows `—` for most rows.
- **Pass rate** is clipped mid-glyph: cells read `0'` and `1(` where `0%` and
  `100%` belong.
- **Timing** is squeezed against the right edge.

## Evidence — the cause is written into the code

`IntelligenceHubPage.tsx:718-742`:

```tsx
{/* Column budget (measured live at a 1345px viewport, where the
    runs panel is 641px): the four fixed columns must fit in
    ~442px so Build keeps a readable ~200px. Without caps they
    took 631px, collapsing Build to 28px AND still overflowing. */}
<Th className="w-full max-w-0 min-w-[150px]">Build</Th>
<Th className="w-[110px] max-w-[110px]">Suite</Th>
<Th className="w-[88px]  max-w-[88px]">Status</Th>
<Th className="w-[86px]  max-w-[86px]">Pass rate</Th>
<Th className="w-[158px] max-w-[158px]">Timing</Th>
```

110 + 88 + 86 + 158 = **442px of hard caps**, and Build is `w-full`.

The layout is therefore correct at exactly one width and degrades in both
directions:

- **Wider than 1345px** — every extra pixel goes to Build, because it is the
  only flexible column. At the reported width Build is roughly twice its
  intended ~200px and the four capped columns never grow, so the row reads as
  one label and a large gap.
- **Pass rate at any width** — `max-w-[86px]` is a hard cap, and the cell
  renders a bar *and* a percentage. The screenshot shows the percentage cut
  mid-character, which is the cap truncating content rather than a data problem.

The comment is honest about its own method: *"measured live at a 1345px
viewport"*. The fix that produced these numbers solved a real collapse (Build at
28px) by pinning four columns to a single measurement. That trades one
viewport's bug for every other viewport's.

## Fix direction (not implemented)

Proportional or `minmax()`-style sizing rather than four fixed caps, so the
columns share slack instead of Build absorbing all of it — and a `min-width` on
Pass rate that fits its own content (bar + `100%`) rather than a `max-width`
that cuts it.

## Tests required when this is picked up

`textContent` cannot see this defect: every value is present in the DOM and only
its *box* is wrong, so a rendering assertion passes while the user sees a cut-off
number. The regression test must read **computed geometry** — the same approach
the 2026-08-29 dashboard-grid defect (`TL-2026-08-29-01-001`) used, asserting
computed track widths.

Minimum coverage:

- Column widths at **two** viewports at least (e.g. 1345px and 1920px), because
  one measurement is what produced this defect.
- The Pass rate cell's `scrollWidth` does not exceed its `clientWidth` — that is
  the clipping, stated directly.

## Why this is backlog and not fixed here

This is a layout change to a shared table on a primary page, and getting it
right needs measurement at several widths against the live deployment. The
program it arrived in was closing out; filing it with the measured cause and the
test requirement is more useful than a quick width tweak that re-pins the same
trap at a different number.
