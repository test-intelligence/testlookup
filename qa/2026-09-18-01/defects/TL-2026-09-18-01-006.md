# TL-2026-09-18-01-006 — The cross-tenant guard stopped reading request bodies, and stayed green

- Reported by: backend baseline run (host), triaging the 24 failures
- Confirmed by: direct introspection of the FastAPI route object, plus a
  mutation back to the shipped accessor
- Severity: **S2, P0** — not an exploitable hole in itself, but half of the
  control that guards against a class of holes this repo has already been bitten
  by nine times was inert, and reported success
- Priority: P0
- Component/surface: `backend/tests/test_architectural_authorization.py`
  (`_non_path_scoped_ids`)
- Journey: EX-05 / EX-06 adjacent
- Status: **FIXED** — merged to `main` in PR #126 on 2026-09-19.
  (The "FIX READY" label below predates that merge and was never updated;
  corrected 2026-09-20 after verifying the change is present on `main`.)

## Reproduction

```bash
cd backend && python -m pytest tests/test_architectural_authorization.py -p no:testlookup
```

Observed on `main` @ `44be1f20`:

```
FAILED tests/test_architectural_authorization.py::test_a_scoped_id_outside_the_path_is_still_checked
E   AssertionError: These NONPATH_KNOWN_EXEMPT entries now check their scope
    (or the route is gone). Delete them — the backlog only shrinks:
      POST   /api/v1/stream/events/batch
```

The message is accurate about the symptom and wrong about the cause. The route
had not become safe and had not gone away. It had become **invisible**.

## Evidence

`_non_path_scoped_ids` reads the Pydantic model behind each body param:

```python
model_fields = getattr(getattr(field, "type_", None), "model_fields", None)
```

Introspecting the live route object:

```
body_params: ['batch']
  has .type_:              False          <-- the attribute does not exist
  getattr type_:           <MISSING>
  field_info.annotation:   <class 'app.models.schemas.LiveEventBatch'>
  annotation.model_fields: ['session_id', 'run_id', 'batch_id', 'events']
```

`field.type_` is not defined on this FastAPI's `ModelField`, so
`getattr(..., "type_", None)` returned `None`, `model_fields` was never reached,
and **no request body in the application was scanned** — only query params were
still being checked.

`LiveEventBatch` carries `session_id`, `run_id` and `batch_id`. All three are in
`SCOPED_IDS`. The route should always have been examined.

This is the failure mode the repo already has a name for: a control that stops
looking reports zero violations, which is indistinguishable from a codebase with
none. It fails **green**.

## Blast radius — measured, not assumed

The detector was patched in a scratch script and both offender sets compared:

```
offenders with the shipped detector:      2
offenders once body models are inspected: 3
newly visible:                            1
  of which not already exempted:          1
    POST /api/v1/stream/events/batch
```

So the practical exposure today is **one route**, and that route is safe on its
merits: its project is resolved server-side from `X-Session-Token` via
`resolve_project_id_for_session`, and the caller cannot name a project. That is
exactly what its `NONPATH_KNOWN_EXEMPT` entry says.

The defect is therefore about the control, not about a live hole. That does not
make it minor: this scan exists because triaging its backlog by hand previously
found **nine real cross-tenant holes**, including two that were missed until
`run_ids` and `test_case_id` were added to `SCOPED_IDS`. Any new route taking a
tenant-owned id in its body would have been waved through.

## A wrong fix that the guard's own message invites — and which I made first

The failure says "Delete them — the backlog only shrinks", so the obvious move
is to delete the exemption. **I did, and the module went green: 52 passed.**

It was wrong, and mutation testing is what caught it. Removing
`resolve_project_id_for_session` from the handler body — which should have made
a genuinely-scoped route reappear as an offender — changed nothing. The route
was not passing the scope check; it was never reaching it.

Had that deletion shipped, the exemption would have been gone while the route
stayed exactly as unscannable as before, and whoever later fixed the accessor
would have been met by a *new* unexplained offender in CI.

## Fix

1. `_body_model(field)` reads `field.type_` and falls back to
   `field.field_info.annotation`, so the scan works across FastAPI versions and
   keeps working if the accessor moves again.
2. The `POST /api/v1/stream/events/batch` exemption is **restored**. It was
   never stale on its merits.

## Tests added (MANDATORY — both)

- Unit: `test_the_body_scan_can_actually_see_into_a_request_body` in
  `backend/tests/test_architectural_authorization.py`. It fixes a concrete
  subject — a real route whose body model carries `SCOPED_IDS` entries — and
  asserts the scan reaches that model, rather than asserting on the accessor's
  name. Runs in CI via the `backend-test` job.
- E2E: none, and deliberately so. This defect is in a static source scan; there
  is no runtime behaviour to drive through the UI. The user-facing counterpart
  is EX-06's live cross-project probing, which found no leak on the surfaces it
  covered. Recording the absence rather than adding a decorative spec.

Both preconditions in the new test carry their own assertion messages, so if the
route is retired or its model loses its scoped ids, the test says the
precondition is gone instead of passing vacuously.

## Verification evidence

- Green after fix: **54 passed**.
