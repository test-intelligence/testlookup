# TL-2026-09-18-01-009 — Selecting a different run on `/agents` leaves the previous run's data on screen

- Reported by: **user**, 2026-09-18 — "the dropdown 'Pipeline Runs': when a run
  is selected the data in the page is not refreshed"
- Confirmed by: source trace of the state that drives every detail panel
- Severity: S2 (the page shows one run's header over another run's data)
- Priority: P1
- Component/surface: `frontend/src/pages/AgentStatusPage.tsx`
- Status: **FIXED** on `qa/exploratory-e2e-2026-09-18` — but only **half** the
  defect. Clearing the stale pipeline id stopped the panels describing the
  previous run and left them describing *nothing*, so the user reported the same
  sentence again the next day. Completed 2026-09-20 as **BUG-011** (the run now
  opens its newest pipeline); see `LIVE_APP_BUG_TRACKER.md`. Read this record as
  "the stale-id half", not as the whole fix.

## Reproduction

1. Open `/agents` and choose a run in the "Test Suite & Build" dropdown (the
   control under the **Pipeline Runs** heading).
2. Click a pipeline card so its stages, timeline and AI report render.
3. Choose a **different** run in the same dropdown.

Expected: the whole page describes the newly-selected run.

Observed: the header and the pipeline list update, but the stage detail,
timeline, compute graph and AI report keep showing the previous run.

## Evidence — the mechanism

The dropdown navigates (`AgentStatusPage.tsx:686`):

```tsx
if (id) navigate(`/agents/run/${id}`)
```

so `runId` changes and `usePipelines(runId)` refetches correctly — which is why
the list looks right and the bug reads as "only part of the page refreshed".

But the detail panels are keyed on separate component state:

```tsx
const [selectedPipeline, setSelectedPipeline] = useState<string | null>(null)
const { data: stages }   = usePipelineStages(selectedPipeline)
const { data: timeline } = usePipelineTimeline(selectedPipeline)
```

`grep -n setSelectedPipeline` returns exactly two call sites: the
`useProjectChangeReset` callback, and the pipeline card's `onSelect`. **Nothing
clears it when `runId` changes.** So after switching runs, `selectedPipeline`
still holds the previous run's pipeline id and every panel below the header
keeps rendering it.

The project-change case had already been noticed and handled
(`useProjectChangeReset`). The run-change case — the far more common action on
this page — had not.

## Fix

Clear the selection when `runId` changes:

```tsx
useEffect(() => {
  setSelectedPipeline(null)
  setSelectedRunId(null)
  setShowSummary(true)   // matches the card-click path
}, [runId])
```

Reset on `runId` rather than validating the stored id against the refetched
pipeline list: the list arrives a tick later, so a check against it would render
the stale pipeline in the meantime.

## Tests added

- Unit: `frontend/src/pages/AgentStatusPage.runswitch.test.tsx` — runs in CI via
  the `frontend-test` job.

The assertion is on **the id the detail hooks are called with**, not on rendered
text. The panels are what went stale and they are driven entirely by that
argument; a text assertion would pass as soon as any panel rendered anything,
including the stale one.

## Verification evidence

- Green after fix: 1 passed. Full `AgentStatusPage` suite: **4 files, 24 tests,
  0 failures** — the new effect breaks none of the existing behaviour.
- Mutation — change the dependency array to `[]`, which is what "clear the

  `the previous run pipeline is still driving the stage panel: expected 'pipe-1' to be null`.
