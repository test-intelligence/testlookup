# TL-2026-09-18-01-008 — "0 flaky" on the summary report beside "1 quarantine" on Flaky Coach

- Severity: S3 if the numbers are correct (they do not explain themselves), S2 if
  they are not
- Priority: P2
- Component/surface: `/reports/summary`
  (`backend/app/services/summary_report_service.py:145`) and `/flaky-coach`
  (`frontend/src/pages/FlakyCoachPage.tsx:224-230`)
- Status: **BACKLOG — investigation, not yet reproduced by this program**

## What was reported

`/reports/summary` shows **0 flaky** for a project while `/flaky-coach` shows
**1 quarantine**.

## Analysis from the source — the two numbers are not the same measurement

This is the most likely reason they differ, and it means "0 and 1" can both be
correct at the same time.

**Summary report — a behavioural measurement.**
`summary_report_service.py:145` calls `metrics_service._count_flaky_tests`,
whose docstring gives two conditions, *both* required:

> * failure ratio inside 10%-90% (it neither always passes nor always fails), and
> * at least `_FLAKY_MIN_FLIPS` pass↔fail transitions **in run order**.

The second condition exists deliberately: without it "a permanently-broken test
was reported as flaky, which points a QA lead away from a real bug". So this
counts tests *currently behaving* flakily over their last N executions.

**Flaky Coach — a workflow state.** Quarantine rows move through
`DETECTED → PROPOSED → APPROVED → QUARANTINED → RECHECK_SCHEDULED → …`
(`models/postgres.py:5730-5760`). A row exists because somebody or some agent
acted, not because the test flipped this week.

**And the states interact in the direction that produces exactly this pair.**
The state machine says of `QUARANTINED`:

> test cases tagged 'quarantined', **excluded from release gate scoring**

A quarantined test is suppressed. Suppressed tests stop producing new pass↔fail
transitions, so they stop satisfying the behavioural definition and legitimately
drop out of the flaky count — while their quarantine row stays live by design
until the recheck window closes.

**"0 flaky, 1 quarantined" is therefore the expected steady state after a
successful quarantine**, not obviously a defect.

## Check this first — it is cheaper than either of the above

`/flaky-coach` is one of the nine routes in `frontend/src/config/routeScope.ts`
that render only with **exactly one project pinned**. `/reports/summary` is not.
If the two pages were viewed under different scopes — one project pinned versus
All Projects — the numbers describe different populations and nothing is wrong
with either.

Confirm the project selector showed the same project on both pages before
investigating anything deeper.

## Also worth confirming: which number Flaky Coach actually showed

`FlakyCoachPage.tsx:224-230` renders **two** figures in one subtitle:

```tsx
const candidateCount = coach?.quarantine_candidates ?? 0
subtitle={`${flakyCount} flaky test… · ${candidateCount} quarantine candidate…`}
```

A *quarantine candidate* is not an active quarantine. If the reported "1
quarantine" was the candidate figure, then Flaky Coach's own `flakyCount` is the
number to compare against the summary report — and if those two disagree, that
is a genuine defect, because both are meant to be the same measurement.

## How to settle it

Against the deployment, for the same project id:

```sql
-- what the summary report counts (behavioural, last N runs)
--   run metrics_service._count_flaky_tests for the project, or read
--   GET /api/v1/reports/summary  -> flaky_test_count

-- what Flaky Coach counts (workflow rows)
SELECT status, count(*)
  FROM flaky_quarantines
 WHERE project_id = :pid
 GROUP BY status;
```

Then:

| Finding | Verdict |
|---|---|
| Different project scope on the two pages | Not a bug. Consider scoping the summary report or labelling the scope on both |
| Quarantine row is `QUARANTINED`/`RE_QUARANTINED` and the test no longer flips | **Accurate**, and the defect is that neither page says so |
| Flaky Coach's own `flakyCount` ≠ the summary report's `flaky_test_count` | **Bug** — one measurement, two answers |
| A live quarantine exists for a test that still flips and is not counted | **Bug** in `_count_flaky_tests` scoping |

## If accurate — the fix is wording, not arithmetic

A QA lead reading "0 flaky" reasonably concludes there is no flakiness, while a
quarantine is active precisely *because* there was. The summary report should
say what it excludes — e.g. "0 flaky · 1 quarantined (suppressed)" — so the two
pages stop appearing to contradict each other.

Related prior art in this repo: `feedback_summary_report_count_semantics` and
`feedback_flaky_coach_total_counts_flips` both record count-semantics drift
between surfaces.
