## Step 3 — completeness: **DEFECT FOUND AND FIXED** (TL-2026-09-19-01-004)

The plan asks that clusters cover all failures "or an explicit `N unclustered`".
Neither held: `failure_clusters` was `[]` on a run with 2 failures, and the
string `unclustered` does not exist anywhere in the codebase.

The cause is not the cluster agent. It returns `[]` only when there are no failed
tests — and it never ran: `failure_clustering` belongs to `DEEP_REQUIRED_STAGES`,
so an `offline` pipeline has no clustering stage at all. `pipeline_stages`
confirms it (ingestion, anomaly_detection, root_cause_analysis, summary,
triage) and `deep_pipeline_status` reads `never_run`.

The card rendered that as **`Anomalies / 0 / no clusters`** — an affirmative
measurement of something never measured, on a run with real failures. A reader
takes it as "the failures were analysed and found unrelated".

Fixed: `—` with "not run — deep investigation only" when clustering did not run,
"no clusters found" only when it did. The flag is derived from the stage list
rather than the workflow name, so it survives clustering being added elsewhere.
The stat is relabelled **Clusters**, because it was labelled "Anomalies" while
showing a cluster count and the payload carries no anomaly count to use instead.

## Step 4 — edge cases: **measured**, six runs

| build | status | total | pass | fail | skip | pass_rate | report bytes |
|---|---|---|---|---|---|---|---|
| a-zero-failures | PASSED | 6 | 6 | 0 | 0 | **100** | 7,073 |
| b-one-failure | FAILED | 3 | 2 | 1 | 0 | **66.67** | 7,562 |
| c-all-fail | FAILED | 4 | 0 | 4 | 0 | **0** | 9,255 |
| d-only-skips | **STOPPED** | 4 | 0 | 0 | 4 | **0** | 6,923 |
| e-no-trace | FAILED | 2 | 1 | 1 | 0 | 50 | 7,565 |
| f-huge-log | FAILED | 2 | 1 | 1 | 0 | 50 | **7,565** |

Every one produced a report, and all six auto-triggered a pipeline that reached
`completed` — incidental confirmation that the beat fix holds beyond its own
regression test.

Two results worth stating:

- **A run where nothing executed is `STOPPED` with pass_rate `0`, not `PASSED`
  with `100`.** This is the exact trap `canonical_pass_rate` guards
  (TL-2026-09-19-01-001) — "we tested nothing" must not read as "everything
  passed" — and the ingest path gets it right independently.
- **The 2 MB single log line did not reach the report.** `f-huge-log`'s envelope
  is 7,565 bytes, byte-identical in size to `e-no-trace`. It ingested without
  error and the payload was not bloated.

A failure with an **empty stack trace** was handled with no error; its analysis is
indistinguishable from the others, all of which failed for want of an LLM.

## Step 5 — provenance: **passes**

```json
{"schema_version": 2, "fallback_used": true, "generated_by": "ai_pipeline",
 "tools_used_count": 0, "confidence": 19,
 "confidence_reason": "Low confidence: No evidence artifacts collected; baseline
   comparison available; LLM was unavailable — deterministic analysis only.",
 "evidence_count": 0, "sources_used": [],
 "deterministic_checks_used": ["baseline_comparison", "regression_classification"]}
```

Confidence carries a stated reason naming what was and was not available; the
deterministic checks that *did* run are listed by name; and the report carries
`ai_disclaimer` ("AI-generated. This report is a draft until a human reviewer
accepts it"). Per-failure records are equally honest — `root_cause_summary:
"Analysis failed — manual review required"`, `requires_human_review: true`,
`recommended_actions: ["Review stack trace manually", "Check LLM service
connectivity"]`. **No placeholder shipped as fact.**

## Checked and deliberately NOT filed

- **`avg_confidence: 0.0`.** Looked like "absence reported as a measured zero",
  but the page surrounds it with a `gaps` entry ("No evidence artifacts
  collected") and an explicit explanation that "the LLM reasoning layer was
  unavailable. Treat the verdict as a deterministic fallback". The number is
  contextualised, not bare.
- **`all_green: true` on the skip-only run.** `d-only-skips` executed nothing yet
  the report says all green (`all_green = failures_known and not failed_ids`).
  That reading is correct for its original purpose — the planner uses it to skip
  analysis stages, and a run with no failures genuinely has nothing to analyse.
  Crucially, **no component renders it**: `allGreen` is exposed by
  `useRunIntelligence` and has zero `.tsx` consumers, so there is no
  user-visible claim today. Recorded as a latent trap for the first consumer that
  reads it, not filed as a defect and not "fixed" speculatively — changing the
  planner's definition would break correct stage-skipping.
- **A `stage` vs `stage_name` mismatch.** My probe read
  `s.get('stage') or s.get('stage_name')`, and the `or` hid which key was real.
  The payload and the `PipelineStage` interface both use `stage_name`; there is
  no contract drift. A lenient accessor nearly manufactured a finding.
