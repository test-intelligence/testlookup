Status: **all six steps addressed.** 1, 2, 5 and 6 measured and passing (5 after a
fix); 3 and 4 measured and found wanting, recorded rather than filed.

Measured against the local stack, project *E-Commerce Platform*.

## Step 1-2 — aggregation and metrics: **PASS**

The plan is explicit: "re-derive independently with SQL, do not trust the page's
own second number." The service's semantics were read first (`_window_totals`:
`DISTINCT ON (test_fingerprint)`, status from each fingerprint's most recent
execution in the window), then re-implemented as a separate query.

```
API  112 | 85 | 21 | 5 | 1 | 75.9 | 79.4
SQL  112 | 85 | 21 | 5 | 1 | 75.9 | 79.4
```

Exact match on all seven values. The four composition rates sum to 100.1%, so
they are a genuine partition over `total` — which is *why* `pass_rate_pct`
divides by `total` rather than `evaluated`.

The plan's own spec is stale here: it lists `GET /api/v1/summary-report`, but the
router prefix is `/api/v1/reports/summary`. The former 404s.

## Step 3 — temporal split: **measured, recorded, not filed**

The requirement: "a 30-day window must not hide a 1-day incident — assert the
daily series, not just the window aggregate."

**There is no daily series.** `runs_per_day` is a scalar mean (7.1 = 213/30), and
the page has a single data source (`useSummaryReport`) with no trend, series or
chart. The aggregate really does hide variation — per-day pass rates inside that
same window:

```
2026-08-24  63.4      2026-08-23  90.5
2026-09-19  64.0      2026-08-22  92.9
2026-08-25  70.7      (window aggregate: 70.5 / weighted 75.8)
2026-08-21  81.0
2026-08-26  85.7
```

A **29.5-point spread**, invisible on this page.

Not filed, because `/trends` is the product's temporal surface and this page does
not claim to be one. Whether a summary should carry a sparkline or a "worst day"
figure is a product decision. The numbers are recorded so it can be made.

## Step 4 — insights cite their runs: **measured, gap recorded**

There is **no `insights` key** in the response, so the step's literal subject does
not exist. The nearest equivalents make claims without citing them:

```
top_failing_tests[]  keys: class_name, failure_step, failures, step_breakdown,
                           suite_name, test_name          <- no run reference
suites[]             keys: ..., last_run_at               <- a timestamp, no id
```

So the report states "`test_case_023` — 12 failures" with no way to reach those
twelve runs, and the UI does not compensate: the rows carry no `<Link>`,
`onClick`, `navigate` or `href`.

Recorded rather than fixed. Adding citations means a payload change plus UI
navigation, and *which* run a row should cite (latest? all twelve?) is a product
decision, not an implementation detail.

## Step 5 — export: **DEFECT FOUND AND FIXED** (TL-2026-09-19-01-005)

The PDF is numerically faithful — all thirteen published values appear, verified
against an API response that was itself verified against independent SQL. But
`basis`, `unique test` and `per test execution` were **all absent**, leaving
"Pass % 70.5%" beside "Weighted pass % 75.8%" with nothing to explain either.

The page does not have this problem. The PDF is the *detached* surface — emailed,

## Step 6 — shared-report scope: **PASS**, design and empirical

A share link carries no recipient identity, so the link *is* the scope. That is
the right shape, and it is implemented carefully:

- the token is looked up by **SHA-256 hash**, so a database leak yields no usable
  tokens;
- `is_revoked` and `expires_at` are both enforced, raising to a 403;
- the report is composed from **`link.run_id`** — taken from the validated link,
  never from the request — so there is no user-controllable id and no IDOR
  surface;
- an additional publication gate (`decide_run_distribution`) refuses an
  unreviewed AI report on this channel, with the comment "a share link is the
  most exposed channel";
- access is written to `AccessAuditLog`.

Probed live:

| token | result |
|---|---|
| `invalid-token-abc` | **403** |
| 64 hex zeros (well-formed, nonexistent) | **403** |
| `../../etc/passwd` | **404** (no route match) |
| `' OR 1=1--` | **403** |

The injection string returns 403 rather than 500 because the token is hashed
before it reaches the query — injection is neutralised by construction, not by
escaping.
