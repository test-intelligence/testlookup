## What was measured

**Steps 3-4 — drive a failure and a skip into a run; assert aggregates match the
per-test rows.** A JUnit file with a deliberately distinguishing mix (10 tests:
6 passed, 2 failed, 2 skipped) was ingested through the real HTTP endpoint:

```
POST /api/v1/ingest/file  project=ecommerce-platform  build=JR02-SKIPS-001
  -> 202 {"status":"accepted","run_id":"0613ab2f-…","task_id":"6d69480e-…"}
  -> stored: total=10 passed=6 failed=2 skipped=2 broken=0
             pass_rate=75  duration_ms=4100  status=FAILED
```

The mix was chosen so the two candidate formulas differ: `6/8 = 75.0` (canonical)
vs `6/10 = 60.0` (skips in the denominator). **75** is correct.

`duration_ms=4100` equals the sum of the per-case times
(0.4+0.35+0.41+0.5+0.47+0.52+0.9+0.45+0.05+0.05 s) — an independent
re-confirmation of the TL-2026-09-18-01-005 fix in a second environment, on a
different host, through a different ingest.

Aggregates were then cross-checked against the rows themselves for three seeded
runs. The four status counts matched `test_cases` **exactly** in every case.

## Defect found — TL-2026-09-19-01-001 (fixed)

Only `pass_rate` disagreed, and only on seeded runs. Both demo seeders used
`passed / total`, the formula `ingestion.py`'s own comment says was replaced.

```
runs_with_cases       294
diverging              28
  with skips           28
  without skips         0      <- the control
worst_delta          8.47 percentage points
```

All 28 diverging runs have at least one skip and **no run without skips
diverges**. That control is what identified the denominator rather than some
other arithmetic fault. Fixed by moving the rule into `app/core/pass_rate.py`
and importing it in both seeders. See the defect file for the full record.
