# JR-03 — AI Pipeline Journey

Status: **partial** — unblocked and largely measured. Steps 1, 5 and 6 measured;
2 and 4 partly; **step 3 (error paths) not measured at all**.

Originally blocked. The blocker was a real defect in this repo's Celery
configuration, fixed in `efaa7443`, and the journey was re-run afterwards.

## The blocker was a product defect, not a broken laptop

Step 1 is "confirm the pipeline auto-triggers on run completion". No pipeline
appeared for the JR-02 run. The obvious write-up — "the AI pipeline never
auto-triggers, S2" — would have been **wrong**. What was actually happening:

```
celery/app/base.py send_task -> self.backend.on_task_call(P, task_id)
celery.beat.SchedulingError: Couldn't apply scheduled task
  relay-pending-notification-deliveries: Retry limit exceeded while trying to
  reconnect to the Celery result store backend.
```

Beat is fire-and-forget, but `send_task` subscribes to the result backend unless
the call passes `ignore_result`. With the Redis backend that starts a **pub/sub
result consumer per dispatched task** inside the long-lived beat process. They
accumulate until the backend connection cannot be re-established, and beat dies.

After that it still logs "Sending due task" while nothing lands, and the
container still reports healthy. Measured: the worker received **zero** tasks for
20+ minutes, every queue sat at depth 0, and 20 `run_downstream_outbox` rows were
`pending` with `attempts=0` — no pipeline, no webhooks, no notifications.

It presents exactly like a broken outbox relay. It is not: invoking
`claim_downstream_dispatches` in-process claimed all 20 rows and transitioned
them correctly (rolled back, no lease consumed).

Two reasons the obvious fixes fail: `conf.task_ignore_result` is **not** read by
`send_task` (the flag comes from per-call options), and beat reaches `send_task`
rather than `Task.apply_async` because the task is not registered in the beat
process — so a task-level attribute is not consulted either. The option has to be
on the schedule entry, and it is injected in a loop over all 45 rather than typed
into each.

**After the fix**, in a 90-second window: 0 connection-lost errors, 0
`SchedulingError`s, 12 sends; the worker resumed receiving (including
`recover_waiting_run_finalizations`, the task that had killed beat); the outbox
drained 20 → 0.

## Step 2 — stages: **partly measured, and the plan's premise is stale**

```
ingestion            completed    29 ms
anomaly_detection    completed    50 ms
root_cause_analysis  completed  1167 ms
summary              completed   470 ms
triage               skipped        —
```

The plan asks to "assert each stage's status renders — **including `partial`**
(historically unrendered)". **`partial` no longer exists.** E7.1 (2026-09-11)

date here, not the product.

That also explains why all 306 pipelines read `completed`: degraded runs are
completed too, so "all terminal" does not mean "nothing ever failed".

## Step 3 — error paths: **NOT MEASURED**

Across **306 pipelines / 1552 stage results: zero failed stages, zero errors.**
Every stage is `completed` or `skipped`.

So the error path has never executed in this environment, and nothing here
confirms that a failing stage reaches a terminal state with a reason rather than
hanging. **The absence of failures is not evidence that failures are handled.**

"Kill the LLM provider mid-run" is also not directly runnable on `make dev`:
`AI_OFFLINE_MODE` defaults on and the core stack ships no Ollama, so there is no
provider to kill. One adjacent fact was observed —
`summary_provenance.fallback_used: true` — which shows the summary stage takes a
documented fallback when no LLM is available and still reaches a terminal state.
That is not the same as a mid-run provider kill.

To measure this properly: run `make dev-llm`, let a pipeline reach the LLM stage,
stop the Ollama container, and assert the pipeline lands terminal with a reason
and that `reap_stuck_agent_pipelines` is not what rescues it.

## Step 4 — retry/cancel: **partly measured**

`POST /agents/pipelines/{id}/retry` on a completed pipeline returns **409** with
a usable body:

```json
{"message": "Pipeline finished successfully; nothing to retry",
 "status": "completed", "links": {"rerun": "/api/v1/agents/pipelines/trigger"}}
```

Refuses, explains, and points at the correct endpoint.

**Not measured:** retry of a *failed* pipeline, which is the case the plan cares
about — "assert a retried task passes `owner=` so the dedup lock cannot silence
its own retry". There is no failed pipeline to retry (see step 3), so this is
untested. Cancel was not exercised either.

## Step 5 — determinism: **PASSES** (substantive output identical)

The same run was analysed twice (`feda19e0`, then `7c958dfc` via
`POST /agents/pipelines/trigger`). Comparing `result_data` per stage:

| stage | identical ignoring `_replay` |
|---|---|
| ingestion | **yes** |
| anomaly_detection | **yes** |
| root_cause_analysis | no — one key |
| summary | no — one key |

The two differences are metadata, not analysis:

- `adaptive_concurrency.latency_ewma_seconds`: `None` → `0.5375`. A runtime EWMA;
  the first run has no history. Legitimately volatile.
- `summary_provenance.input_fingerprints.analyses_sha256` differs, while **all
  five other fingerprints are identical** — including `ordered_analysis_ids_sha256`.
  Same analyses, same order, different serialised content.

**A raw hash comparison reported "all four stages differ" and that was my
instrument, not the product.** Every stage carries a `_replay` block whose
`input_checksum_sha256`, `output_checksum_sha256` and `attempt_idempotency_key`
are per-attempt by construction. Those checksums feed checkpoint restore *within*
one pipeline run and `_stage_summary` reporting — they are not cross-run replay
keys — so differing across two separate pipelines is correct behaviour. Filing
"the replay fingerprint never matches" would have been a false S2.
