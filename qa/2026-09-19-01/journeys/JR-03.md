# JR-03 — AI Pipeline Journey

Status: **blocked — not measured.** The blocker is environmental and was proven
so rather than assumed.

## What happened

Step 1 is "confirm the pipeline auto-triggers on run completion". For the JR-02
run, no `agent_pipeline_runs` row ever appeared. The obvious conclusion — "the AI
pipeline never auto-triggers" — would have been an S2 defect and **it would have
been wrong**.

What the evidence actually showed, in order:

1. `post_ingestion_operations_staged ai_requested=True` — AI *was* requested.
2. `run_downstream_outbox` held five rows for the run — `agent_pipeline`,
   `run_completed_webhook`, `run_notifications`, `suite_comparison`,
   `transition_notifications` — all `pending`, **`attempts=0`**, no error,
   `next_attempt_at` NULL, 23 minutes old. Across all runs: every row `pending`,
   none ever terminal.
3. `attempts=0` is the tell. The relay had not failed on them; it had never tried.
4. `relay-run-downstream-outbox` **is** in the beat schedule and had fired 279
   times. (An earlier `head -30` of the beat task list truncated before it and
   briefly suggested it was absent — a measurement artefact, not a finding.)
5. The worker's last log line was 23 minutes old and it had received only
   `ingest_uploaded_file` and `reindex_search`. Queue depths all 0. Brokers
   identical (`redis://…/0` for both beat and worker), so not a shard mismatch.
6. Beat's own log: `Connection to Redis lost: Retry (18/20)`. Redis itself
   answered PONG with 55 clients and was saving normally — the fault is
   beat-side, and it survived a `docker restart`.

**So beat logs "Sending due task", then the publish fails.** Nothing lands, and
every periodic task silently stops.

## The relay logic is correct — verified directly

Rather than infer it, `claim_downstream_dispatches` was invoked in-process:

```
CLAIMED: 20
   agent_pipeline -> sending attempts= 1
   run_completed_webhook -> sending attempts= 1
   …
```

It claimed all 20 pending rows and transitioned them correctly. The transaction
was rolled back, so no lease was consumed. The outbox works; the broker does not.

Steps 2-6 (stage statuses including `partial`, killing the LLM provider
mid-run, retry/cancel with `owner=`, determinism, p50/p95 latency) all depend on
a pipeline actually running, so **none were measured**.

## Finding — BUG-010 (filed, not fixed)

Independent of the broker, and verified by `git grep` over the tracked tree:
`ai_pipeline_debouncer.enqueue_pipeline_for_run` has **zero production callers**.
The only non-test reference is a *comment* at `celery_app.py:169`. Yet
`config.py:304-309` states "`stream_service.close_session` no longer fires
`run_agent_pipeline` directly; the run lands in a Redis SortedSet", and
`stream_service.py` references neither the debouncer nor `run_agent_pipeline`.
`AI_PIPELINE_DEBOUNCE_ENABLED` defaults to **True**, and
`flush-ai-pipeline-queue` runs every two minutes draining an empty set.

The live mechanism is the outbox. The debouncer is dead code whose configuration
describes it as live — an operator would tune
`AI_PIPELINE_DEBOUNCE_WINDOW_SECONDS` and see no effect.

**Deliberately not fixed.** The worktree `agent-a08622553ca10f607`
(`feat/epic3-gitlab-integration`) is adding the missing call at
`stream_service.py:500`. Deleting the module or its beat entry here would
conflict with that active work, and wiring it as-is risks double dispatch
alongside the outbox. Which mechanism is canonical is an owner decision.
