# JR-06 — Release Gate Journey

Status: **partial.** The fail-closed layering was inspected and one real defect
found and fixed. The policy/band matrix and the override path were not measured.

## What was measured

`GET /api/v1/release-readiness/0613ab2f-…` on the JR-02 run — 75.0% pass rate, 2
failures, and **no AI pipeline had run**:

```
recommendation = CONDITIONAL_GO   risk_score = 35   composite_risk = 35.2
blocking_issues = []              conditions_for_go = []
dimension_scores: user_impact     100.0 (w .25)  env_sensitivity  0.0 (w .10)
                  reproducibility  25.0 (w .15)  regression_likely 0.0 (w .20)
                  hist_recurrence   0.0 (w .10)  blast_radius     10.0 (w .15)
```

**Fail-closed layering — verified in source, not assumed.** Two independent
floors exist:

- a hard floor: `pass_rate < threshold * HARD_FLOOR_FACTOR` (90.0 × 0.7 = 63.0)
  forces composite ≥ 60 → NO_GO regardless of the risk model. 75.0 clears 63.0,
  so the composite decided this verdict.
- `_apply_band_floor`, documented "Fail-closed: the band can downgrade the
  verdict but never soften it."

R4 ("release gate returns a decision on incomplete evidence") is **real but
mitigated**. Three dimensions scored `0.0` — not because those risks were
measured and found absent, but because no per-test analyses existed. The code
comment assumes the analyses are "produced by the offline pipeline's analysis
stage, which has already run by the time this endpoint is called", and that was
**false here**. The hard floor is what stops it becoming a false GO. The verdict
also labels itself honestly: "Quick-look decision derived from this run's
aggregates … Run Deep Investigation for richer insights."

## Defect found — TL-2026-09-19-01-003 (fixed)

`CONDITIONAL_GO` with `conditions_for_go = []`, and `ReleaseGatePage.tsx:457`
renders that block behind `.length > 0` — so the section is **hidden entirely**.
A release manager saw a conditional verdict with no conditions anywhere on the
page. Fixed with `_quick_look_conditions(...)`, which states only what the path
actually gates on, including explicitly that the analysis dimensions were **not
measured**. No verdict changed. Full record in the defect file.

Worth recording: `test_release_gate_snapshot_explains_verdict.py` documents a
2026-08-07 sweep concluding CONDITIONAL_GO was unreachable on this path
(composites jumped 13 → 60, skipping the entire [20,55) band). That sweep used a
throwaway project with **no open defects**. This run's project had **79**, lifting
`user_impact` to 100.0 and the composite to 35.2 — inside the band. The
"unreachable" case is reachable in any project with a real backlog, which is
every real project.

## Not measured

The policy matrix, which is most of the journey:

- create a `ReleaseGatePolicy` → publish → 100% run (expect GO) → 88.9% run
  (expect NO_GO) → **boundary runs exactly at each band edge** → hard-cap
  violation (P0 > 0).
- `POST /release-readiness/{run_id}/override` with justification; the override
  being audited; and `release.decided` actually being **emitted** rather than
  merely declared — the plan flags this as a known "declaration is not emission"
  risk and it remains unverified.
- `/policies` and `/releases` surfaces untouched.

Band boundaries are the highest-value unmeasured item. "Inclusive/exclusive
exactly as the policy states" is precisely where an off-by-one flips a ship
decision, and a threshold sitting on the wrong side of a boundary is a defect
class this program has already hit twice — the `/intelligence` Build-share
threshold that passed against its own defect, and the 2026-08-07 sweep above.
