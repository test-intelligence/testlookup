# JR-06 — Release Gate Journey

Status: **substantially measured.** Fail-closed layering verified; band edges
measured and **correct**; hard-cap semantics measured and produced a
documentation defect; `release.decided` emission measured and produced a second
one. Policy lifecycle and override not measured.

## Earlier slice

Quick-look verdict on a run with no AI analysis returned `CONDITIONAL_GO` with an
empty `conditions_for_go`, fixed as TL-2026-09-19-01-003. The fail-closed
layering was verified in source: a hard floor
(`pass_rate < threshold × HARD_FLOOR_FACTOR`, 90.0 × 0.7 = 63.0) and
`_apply_band_floor`, documented "the band can downgrade the verdict but never
soften it".

R4 ("the gate returns a decision on incomplete evidence") is real but mitigated:
three dimensions score `0.0` when no per-test analyses exist — not measured, not
measured-and-absent — and the hard floor is what stops that becoming a false GO.

## Band edges: **no defect**

The plan flags this as the highest-risk item — "inclusive/exclusive exactly as
the policy states" is where an off-by-one flips a ship decision. Every edge
measured against `classify_with_policy`:

| pass rate | band |
|---|---|
| 99.0 (`green_min`) | **green** |
| 98.99 | yellow |
| 95.0 (`yellow_min`) | **yellow** |
| 94.99 | orange |
| 90.0 (`orange_min`) | **orange** |
| 89.99 | red |

Every comparison is `>=`, so each `*_min` is inclusive of its own band —
consistent with the `_min` naming and uniform across all four bands. **No
off-by-one.** Now pinned by a parametrised test.

## Hard caps: a real trap, but in the docs — TL-2026-09-19-01-006

Measured:

```
caps = {max_p0_defects: 0, max_flaky_count: 0, max_new_failures_24h: 0}

100% pass, 25 flaky, 50 new failures  ->  green  GO     downgrades []
100% pass, 1 P0                       ->  red    NO_GO  downgrades [p0_defects:1>0]
max_flaky_count=1, 25 flaky           ->  red    NO_GO  downgrades [flaky:25>1]
```

**Tightening the flaky cap from 1 to 0 turns enforcement off.** The
stricter-looking value is the permissive one.

I was one step from filing this as an S2 false GO against the fail-closed
mechanism. It is not a defect. `tests/test_classify_with_policy.py` pins the
asymmetry deliberately and explains it: *"P0 and flaky treat 0 differently
because P0=0 is the only intent the user actually wants. `flaky=0` would
over-fire on real projects."* The reasoning is sound and the behaviour intended.

The genuine defect is that this reasoning lived **only in a test docstring**,
while `PolicyHardCaps` — a Pydantic model, so the OpenAPI documentation a policy
author actually reads — stated two things the code does not do:

1. *"`None` (or 0 where `ge=0`) disables the cap"* — false for
   `max_p0_defects`, where 0 is the **strictest** setting, not an off switch.
2. *"exceeding it downgrades the resolved band by one step"* — false. A breach
   pins the band straight to red and forces NO_GO; one-step was replaced
   precisely because yellow still mapped to GO, which made a "hard cap"
   advisory at best.

Both misread dangerously here. Under (1) an author sets `max_p0_defects=0`
believing they have switched P0 blocking *off* and has switched it to maximum.
Under (2) a breach reads as a nudge rather than a block.

Fixed by documentation only — **no behaviour change, and every existing policy
test still passes**. The new tests assert the docs against *live* behaviour
rather than fixed strings, so the two cannot drift apart again.

## `release.decided` emission: measured — TL-2026-09-19-01-007

The plan flagged this as the known "declaration is not emission" risk. **That
specific gap is closed**: the emitter exists, has two production call sites, and
all three points are pinned — proven by mutation, not by reading. Neutering the
emitter so it reports a delivery it never stages fails **7** tests; making the
critic import `emit_release_decided` and never call it (the original defect
shape) fails **1**; silencing the override route fails **1**.

Worth recording: `test_release_decided_webhook.py` — the 22-test suite named for
this event — did **not** catch the critic mutation. Only the critic's own suite
did. Neither file alone covers the wiring.

**But the decision and the announcement have different authors.**
`release_risk_agent` commits the `ReleaseDecision`; only
`DecisionReportCriticAgent._persist` emits, and only when report verification
passes. The failure branch has no emission. A committed, user-visible decision
can therefore go unannounced — and because the row is keyed by `test_run_id` and
updated on re-runs, the subscriber-visible failure is a **stale** value, not a
missing one.

Measured live, read-only:

```
release_risk             completed 236   failed  0
decision_report_critic   completed 160   failed 56
```

The writer never failed; the only emitter failed 56 times. Joining decisions to
their own pipeline's critic: 158 completed, **20 failed**, 22 seeded rows with no
pipeline (excluded). **20 of 178 — 11% — would never have been announced.**

**Not how it shipped.** PR #67 (2026-09-13) emitted from the *writer*, right
after its commit — a design with no gap. Two commits on 2026-09-17 moved it:
`057826a7` "bind queued delivery to exact evidence" added it to the critic, and
`21f1e98f` "bind publication to immutable source" removed it from the writer. So
the 11% is a regression from a deliberate relocation, and the E8.4 reason
(authority follows pipeline + evidence hash) is sound — but nothing anywhere
acknowledges the consequence.

The move updated the module docstring and left **two** public surfaces stale:
`SUPPORTED_EVENTS`, and the `CHANGELOG.md:1177` "Where it fires" contract, which
still states that *both* writes emit. Left unfixed because intended and
unintended imply *opposite* documentation fixes, so guessing would repeat what
produced 006. **Owner decision** — though the CHANGELOG line is wrong either
way.

### Still not measured, and honestly so

Live emission was never observed end to end. `outbound_webhooks` is disabled on
