# TL-2026-09-19-01-008 — A policy changes the verdict without appearing in the provenance

- Found by: JR-06 (policy lifecycle, measured live)
- Severity: **S3** (auditability on the release gate) · Priority: P2
- Component: `backend/app/services/release_council_service.py` — `_apply_band_floor` vs the policy fields
- Status: **REPORTED**, not fixed

## Measured, live

JR-06 could not measure the policy lifecycle because the local database had zero
policies. The homelab has three, so the whole create → publish → observe →
deactivate cycle ran there against project `2aefa4fa`, on run
`8cd0dceb-fa2b-42d0-8cc9-08e7a80362ee` (pass rate **90.91%**).

| state | `recommendation` | `release_readiness_band` | `policy_level` | `policy_id` |
|---|---|---|---|---|
| no policy | `GO` | `None` | `hardcoded` | `None` |
| draft only | `GO` | `None` | `hardcoded` | `None` |
| **published** | **`CONDITIONAL_GO`** | **`orange`** | `hardcoded` | `None` |
| deactivated | `GO` | `None` | `hardcoded` | `None` |

**The plumbing works.** A stored, published policy reaches the classifier: the
band appeared and the verdict moved `GO -> CONDITIONAL_GO`. 90.91% sits between
`orange_min` 90 and `yellow_min` 95, so orange is correct. The draft row is the
control — creating it changed nothing, publishing it did.

That is the JR-06 question answered: **the arithmetic and the plumbing are both
verified, and a published policy can change a ship decision.**

## What is wrong

The two right-hand columns never move. A policy demonstrably drove the verdict,
and the response still reports `policy_level: "hardcoded"` with a null
`policy_id` and `policy_version`.

There is a defensible reading: those fields come from the **stored**
`ReleaseDecision` (`decision.policy_id`, `decision.policy_evaluation`), which
records what the release-risk agent used at write time — and it genuinely used
hardcoded thresholds. The band floor is applied later, at read time, from
whatever policy is active *now*.

But the field a consumer acts on is `recommendation`, and that value is a blend:
the stored decision's verdict, then downgraded by a policy the response does not
name. An auditor asking "which policy produced this CONDITIONAL_GO" is told
"hardcoded, no policy" — about a verdict a policy produced.

`policy_level: "hardcoded"` is also a strong claim rather than a silence. It
does not say "unknown"; it names a source, and that source is wrong for the
value returned.

## Not a defect, recorded to save the next reader

`_apply_band_floor` returns the recommendation unchanged with **no band at all**
when `_resolve_policy_for_project` finds nothing — project-active, then
system-default, then `None`. On this deployment no project with runs has an
active policy and there is no system default, so **all 200 stored decisions
carry a null `policy_id` and the band floor is inert for every one of them.**
That is configuration, not a bug — but it means the band-floor half of the
fail-closed mechanism JR-06 verified in source has never actually fired here.

The hard floor is separate and does not depend on a policy: it falls back to
`settings.RELEASE_PASS_RATE_THRESHOLD` (`policy_evaluator_service.py:143`).

## Suggested fix

Report the policy that produced the returned value. Either surface the read-time
policy alongside the stored one (`band_policy_id` / `band_policy_level`), or set
`policy_level` to something honest like `"hardcoded+band"` when the band floor
moved the verdict. Setting the stored fields from a read-time policy would be
wrong — they describe the write.
