# TL-2026-09-19-01-002 — `/settings` sub-pages had three different ways back, one of which was none

- Reported by: **user**, 2026-09-19, against `http://testlookup.local/settings`
  — "the back button or navigation back to settings is not consistent across all
  the sub-pages ... there should be a consistent approach for all pages"
- Severity: **S3** (navigation dead-end) · Priority: P2
- Tracker: **BUG-009**
- Status: **FIXED** on `qa/journeys-jr02-jr06-2026-09-19`

## Measured, before the fix

23 sub-pages under `/settings/*`, carrying **three** different behaviours:

| Behaviour | Markup | Count | Pages |
|---|---|---|---|
| A — button | `btn-secondary` "**Back**" in `PageHeader actions`, `ArrowLeft h-4 w-4` | 5 | AIConfig, Storage, FeatureFlags, GitHub, Integrations |
| B — breadcrumb | muted "← **Settings**", `h-3 w-3`, above the header | 4 | Billing, GitLab, Retention, OutboundWebhooks |
| — none | *nothing* | **14** | Profile, Notifications, SSO, Audit, ApiKeys, Digests, MfaPolicy, Performance, ProjectData, SeedData, AIAgents, AIEval, AgentActivity, IntegrationHealth |

So the two that existed disagreed on control type, label ("Back" vs "Settings"),
icon size and placement — and **14 of 23 offered no way back at all**, leaving the
browser's back button as the only exit.

Two pages (GitLab, Retention) rendered the breadcrumb **twice**, in two different
render branches.

## Fix — the affordance moved to the layout, not to 23 pages

`frontend/src/components/layout/SettingsBackBar.tsx`, rendered once by
`AppLayout` above `<Outlet />`, keyed off the route.

This is the whole point of the fix. A per-page control is a convention every
future sub-page author has to remember, and 14 of 23 already had not. Rendering
it from the layout means a new `/settings/<thing>` route gets the affordance
without anyone doing anything, so the inconsistency **cannot return one page at a
time**. That is what "a consistent approach for all pages" requires; fixing the
14 individually would have satisfied the report and left the cause in place.

The breadcrumb form won over the button: `PageHeader`'s `actions` slot is where
real page actions live (Save, Create, Rotate), and on the pages that had both,
"Back" read as though it were one of them.

Removed: **11 per-page controls across 9 files**, plus the `ArrowLeft` / `Link`
imports they were the only user of (three of those were multi-line import blocks
a single-line matcher missed — caught by a residual-reference sweep, not assumed).

`isSettingsSubPage` lives in a separate `settingsRoutes.ts` because exporting a
helper beside a component trips `react-refresh/only-export-components`. It
rejects `/settings` and `/settings/` (the index is the destination — a link there
is a loop) and is not fooled by `/settingsomething`, which a naive
`startsWith('/settings')` would match.

## Tests — `SettingsBackBar.test.tsx`, 12 tests

- the predicate: sub-page true; index and trailing-slash index false; prefix
  match `/settingsomething` false.
- rendering: exactly one link to `/settings` labelled "Back to Settings"; nothing
  on the index; nothing outside settings.
- **the route contract** — enumerates every `settings/...` route declared in
  `App.tsx` and asserts each sub-page shows the bar and the index does not. This
  is the test that makes a *new* sub-page unable to ship without it. A
  `/settings/profile` assertion alone would only prove one path works.
- **AppLayout wiring** — the component is imported and rendered, and rendered
  *before* `<Outlet />`.
- **no page re-implements it** — no file under `pages/settings/` links to
  `/settings`. A page-level copy is how the three-way split arose and how it
  would return.
- two presence checks so neither source-reading suite can pass vacuously if the
  route shape or the glob changes.

## Verification

Two mutations, each caught by exactly the guard that should catch it and no other:

| Mutation | Result |
|---|---|
| delete `<SettingsBackBar />` from `AppLayout` | `AppLayout actually renders it > renders it, and above the routed page` **fails** |
| reintroduce `<Link to="/settings">` in `ProfilePage` | `no page re-implements its own back control` **fails** |

The first mutation is the important one. Before I added the wiring test, all 10
other tests passed with `AppLayout` gutted — every case mounts the component
directly, so the suite could not see that no page actually rendered it. That is
the original defect with a green suite.

Both files restored; `git diff` confirms `ProfilePage` is untouched.

- 28 test files / **212 tests** pass across `pages/settings` and
  `components/layout` — no existing test depended on the removed buttons.
- `tsc --noEmit` clean. `eslint` on the changed files: **0 errors, 0 warnings**.
