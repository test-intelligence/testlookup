# TL-2026-09-19-01-003 — CONDITIONAL_GO with an empty `conditions_for_go`, and the UI hides the section

- Found by: JR-06 (release-gate journey)
- Severity: **S3** (a decision surface omits the thing it exists to say) · Priority: P2
- Component: `backend/app/services/release_council_service.py` (quick-look path),
  surfaced at `frontend/src/pages/ReleaseGatePage.tsx:457`
- Status: **FIXED** on `qa/journeys-jr02-jr06-2026-09-19`

## Measured

Run `0613ab2f` ingested through the real endpoint — 6 passed, 2 failed, 2
skipped, pass rate 75.0%, **no AI pipeline had run**. Then
`GET /api/v1/release-readiness/0613ab2f-…`:

```
recommendation    = CONDITIONAL_GO
risk_score        = 35   composite_risk = 35.2
conditions_for_go = []
blocking_issues   = []
reasoning         = "Quick-look decision derived from this run's aggregates
                     (pass rate 75.0%, 79 open defects). Run Deep Investigation
                     for richer insights — failure clusters, defect breakdown,
                     and AI narrative."
```

`ReleaseGatePage.tsx:457` renders the conditions block behind
`decision.conditions_for_go.length > 0`. An empty list therefore does not render
an empty section — **it hides the section entirely**. A release manager saw
`CONDITIONAL_GO` with no conditions anywhere on the page.

The information existed: the `reasoning` prose named the gap. It simply was not
in the structured field the UI reads.

## What is *not* wrong here

The verdict itself is defensible and the path is genuinely fail-closed. Two
layers were verified in the source:

- a hard floor — `pass_rate < threshold * HARD_FLOOR_FACTOR` (90.0 × 0.7 = 63.0)
  forces the composite to ≥ 60 and thus NO_GO. 75.0 clears 63.0, so the
  composite decided.
- `_apply_band_floor`, documented "Fail-closed: the band can downgrade the
  verdict but never soften it."

`input_snapshot` is already meticulous about explicability — it publishes
`no_go_floor_pct`, `hard_floor_factor` and `verdict_driver` so the verdict can be
read from its own payload. The empty conditions list was an omission in that same
spirit, not a wrong decision. **No verdict changes were made.**

One assumption in the code is worth recording, because it was false in this
measurement. The comment above the dimension scoring says the per-test analyses
are "produced by the offline pipeline's analysis stage, **which has already run
by the time this endpoint is called**". Here the pipeline had never run, so
`env_sensitivity`, `regression_likely` and `hist_recurrence` all scored `0.0` —
not because those risks were measured and found absent, but because nothing
measured them. The hard floor is what stops that from becoming a false GO.

## Why this case is reachable at all

`test_release_gate_snapshot_explains_verdict.py` records a 2026-08-07 sweep
finding that this path jumps from composite 13 to 60 and **never enters the
[20,55) conditional band** — so CONDITIONAL_GO appeared unreachable, and an empty
conditions list would never be seen.

That sweep used a throwaway project with no open defects, so `user_impact`
scored ~0. This run sat in a project with **79 open defects**, putting
`user_impact` at 100.0 (weight 0.25 → contribution 25.0) and the composite at
35.2 — inside the band. So the empty-conditions case appears exactly where a
release manager lives: a real project with a real backlog.

## Fix

`_quick_look_conditions(recommendation, pass_rate, threshold)` — extracted as a
named function rather than left inline so the rule is testable. It returns only
conditions this path actually gates on:

1. always, for any non-GO verdict — "Run Deep Investigation — this verdict used
   run aggregates only; failure clusters, regression likelihood and historical
   recurrence were **not measured**." Saying "not measured" is the point: it is
   the difference between *low* risk and *unknown* risk, and absence read as
   health is how a false GO happens.
2. only when `pass_rate < threshold` — "Raise pass rate to at least 90.0%
   (currently 75.0%)", carrying both the target and the current value.

`GO` returns `[]`, which is correct rather than a gap: nothing is outstanding.

Confirmed live after the change:

```
recommendation : CONDITIONAL_GO
conditions_for_go:
  - Run Deep Investigation — this verdict used run aggregates only; failure
    clusters, regression likelihood and historical recurrence were not measured.
  - Raise pass rate to at least 90.0% (currently 75.0%).
```

## Tests — `tests/regression/test_release_gate_conditions_are_stated.py`, 9 tests

- a non-GO verdict is never silent; GO needs none.
- the provisional condition names *what was not measured*.
- the pass-rate condition carries both numbers, and appears **only** below
  threshold — a run held back by something else must not be misdirected toward
  pass rate.
- the threshold boundary is exclusive: 90.0 produces no pass-rate condition,
  89.9 does.
- **the service actually uses it** — asserts `conditions_for_go=[]` is gone from
  the source. The other eight test the helper in isolation and would all pass
  with it wired to nothing.
- no backslash-u escape leaked into the user-facing text. Generating this block
  through a script once wrote the six characters `backslash u 2 0 1 4` into the
  source instead of an em dash, which would have shipped to the UI verbatim. The
  test asserts the string contains a real U+2014 and no `\` + `u` pair.
  (This document hit the same trap: an earlier draft of this very line had its
  escape converted, leaving it reading "a literal — instead of an em dash".)
