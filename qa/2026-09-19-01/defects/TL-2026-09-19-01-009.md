# TL-2026-09-19-01-009 — A release override is not written to the activity ledger

- Found by: JR-06 (override + audit, measured live)
- Severity: **S3** (auditability of the most consequential human action in the product) · Priority: P2
- Component: `backend/app/routers/release_readiness.py`, `backend/app/services/activity/events.py`
- Status: **REPORTED**, not fixed

## What works — measured live

`POST /release-readiness/{run_id}/override` is correct, and its in-row audit
trail is good. Measured on run `4d49527d` (reverted immediately afterwards).

Refusals, all 422 with usable messages:

| input | result |
|---|---|
| `override_recommendation: "SHIP_IT"` | 422, names the three legal values |
| `reason: "   "` (whitespace only) | 422, "Override reason is required." |
| `reason` absent | 422 from the model |
| empty body | 422, both fields named |

The whitespace-only case is the one that is easy to get wrong — a truthiness
check would have let `"   "` through as a justification. It is stripped and
rejected.

The write itself:

```
recommendation           CONDITIONAL_GO -> NO_GO
human_override           the reason text
original_recommendation  CONDITIONAL_GO   (immutable pre-override snapshot)
original_risk_score      22
overridden_by            fc89142e-...
override_audit           [{timestamp, actor_id, actor_name,
                           before_recommendation, before_risk_score,
                           after_recommendation, reason,
                           policy_id, policy_version}]
```

That is a complete, append-only audit entry: who, when, from what, to what, and
why. **The JR-06 question "is the override audited" is answered yes** for the
decision record.

## What is wrong

It is audited *only* there. The override wrote **zero rows** to
`project_activity_events` and **zero rows** to `access_audit_logs` — checked
directly over the window containing it.

That is not an oversight in the catalog. `services/activity/events.py` declares
an event for exactly this:

```python
_spec("release.decision_overridden", "release", "release",
      "Release decision for {entity_label} overridden to {recommendation}",
      "attempt"),
```

**Nothing emits it.** Grepped the whole backend: `release.decision_overridden`
appears once, in the catalog that declares it. `release_readiness.py` never
calls `record_activity` — while **11 other routers do**, including the review
accept path, which records `review.accepted` for a far less consequential act.

`release.decided` is declared as an activity event too (line 216) and is
likewise never emitted as one; its only emitter is the *webhook* subsystem,
which is a different system with a different audience.

## Why it matters

The activity ledger is the cross-cutting "what happened in this project" record.
A QA Lead overriding a release gate — reversing the product's own ship
recommendation — is the single action most likely to be asked about afterwards,
and it is the one action absent from that ledger. The evidence exists, but only
inside the decision row, reachable only by someone who already knows which run
to look at.

Third instance of this pattern in a week, after `release.decided` on the webhook
side (TL-2026-09-19-01-007) and the metric in
`feedback_declaration_is_not_emission`. A declared event with no producer reads
as coverage that does not exist.

## Suggested fix

Call `record_activity` in the override handler after the commit, with
`event_type="release.decision_overridden"`, the actor, and the run as the
entity — mirroring the `review.accepted` call in `routers/reviews.py`. The
catalog entry, including its `{recommendation}` template slot, already exists.

Decide separately whether `release.decided` should have an activity producer or
be removed from the catalog; a declared event nobody emits is worse than no
declaration.
