# TL-2026-09-19-01-001 — Both demo seeders store a pass rate the product calls wrong

- Found by: JR-02 (test-run journey), step 4 — "assert aggregates match the per-test rows"
- Severity: **S3** (demo/seed data, not the ingest path) · Priority: P2
- Component: `backend/scripts/seed_data.py`, `backend/scripts/seed_dev_data.py`
- Status: **FIXED** on `qa/journeys-jr02-jr06-2026-09-19`

## What is wrong

The canonical pass rate, documented in `app/services/ingestion.py:944-952` as the
"single source of truth ... for BOTH file and live ingestion", excludes skipped
tests from the denominator:

```python
executed = passed + failed + broken
pass_rate = round((passed / executed * 100), 2) if executed > 0 else 0.0
```

Both seeders used `passed / total`, which is the formula that comment says was
replaced ("Previously divided by `total` which included skipped"):

| file | line | expression |
|---|---|---|
| `backend/scripts/seed_data.py` | 477 | `round(passed / total * 100, 2) if total else 0` |
| `backend/scripts/seed_dev_data.py` | 639 | `round(passed / total * 100, 1) if total > 0 else 0.0` |

`seed_dev_data.py` is the one `docker-compose.yml:526` actually runs on
`make dev`, so this is what every local developer sees.

## Measured impact, on the local stack

```
runs_with_cases       294
diverging              28
  with skips           28
  without skips         0      <- the control
worst_delta          8.47 percentage points
```

Every diverging run has at least one skip and **no run without skips diverges**.
That control is what identifies the denominator as the cause rather than some
other arithmetic fault — a random defect would not respect that boundary.

The 28 diverging runs are dated 2026-07-28 … 2026-08-26, the seed-data era.

Examples, stored vs the product's own rule:

| run | total | pass | fail | skip | stored | canonical |
|---|---|---|---|---|---|---|
| `e2e892cb` | 42 | 32 | 7 | 3 | **76.2** | 82.1 |
| `75a677d3` | 42 | 29 | 11 | 2 | **69.0** | 72.5 |
| `10b7b3f9` | 42 | 26 | 15 | 1 | **61.9** | 63.4 |

The four status counts match the `test_cases` rows exactly in every case — only
`pass_rate` is wrong. So this is not a counting bug, it is a denominator bug.

## Ingestion itself is correct — proven, not assumed

A file with a known mix was ingested through the real HTTP endpoint rather than
reasoning from the source:

```
POST /api/v1/ingest/file   build_number=JR02-SKIPS-001
  10 tests: 6 passed, 2 failed, 2 skipped
  -> stored: total=10 passed=6 failed=2 skipped=2 pass_rate=75 duration_ms=4100
```

`75` is `6/8`, the canonical value; the seeder formula would have produced
`6/10 = 60`. The two differ, so the measurement can tell them apart.

`duration_ms=4100` also equals the sum of the per-case times
(0.4+0.35+0.41+0.5+0.47+0.52+0.9+0.45+0.05+0.05 s), which independently
re-confirms the TL-2026-09-18-01-005 fix in a second environment.

## Why S3 and not lower

Seeded rows are the baseline a developer or evaluator reads first, so a wrong
number there is not cosmetic — **it is what hides a real regression**.
TL-2026-09-18-01-005 (every ingested run carrying a NULL duration) stayed
invisible for exactly this reason: the seeder filled the column that ingestion
had stopped writing. A regression test pinned against seeded data would have
pinned the wrong number.

## Fix

The rule was restated in six places and two disagreed, so it now lives once:

- **New** `backend/app/core/pass_rate.py` — `canonical_pass_rate(passed, failed,
  broken, *, ndigits)` and `executed_count(...)`. Placed in `app/core/`
  following the precedent `app/core/release_filter.py` set, which
  `summary_report_service` introduced with the note that "a local copy becomes
  two surfaces that can disagree".
- Both seeders import it. `seed_data.py` gained the same
  `sys.path.insert(0, dirname(__file__)/"..")` bootstrap `seed_dev_data.py`
  already uses, so `app` resolves regardless of cwd.
- `ingestion.py` was **left alone**. Its inline computation is already correct
  and is pinned by an existing regression test; rewriting the hot ingest path to
  route through a new module would be risk without benefit.

A run of only skips returns `0.0`, never `100.0` — "we tested nothing" must not
read as "everything passed".

## Tests added

`backend/tests/regression/test_seed_pass_rate_is_canonical.py` — 12 tests:

- the rule itself: `6p/2f` → 75.0; the old formula's 60.0 asserted as *different*;
  BROKEN counts as executed; an all-skips run is 0.0; `ndigits=1` → 79.4,
  matching the live summary report.
- a **source guard** over both seeders: no pass rate may divide by `total`, and
  each seeder must import the shared helper.
- the guard's own self-tests: it matches the exact line deleted from
  `seed_data.py`, and it does **not** fire on `skipped / total`, which is a
  legitimate composition rate.
- a presence check on the seeder paths, so the guard cannot pass vacuously if a
  file is renamed — this fired immediately and caught a wrong `parents[2]` in
  the first draft.

**No browser E2E test.** A Playwright spec cannot see a seeder's arithmetic; it
can only read whatever numbers are in the database, which is the very thing that
concealed this. Adding one would be decoration. The source guard is the
instrument that actually prevents recurrence, so that is where the coverage went.

## Verification

- Mutation — restored `passed / total` in `seed_dev_data.py` and removed its
  import: **exactly the two guards fail**, and only for that module;
  `seed_data.py`'s parametrised cases still pass. Restored afterwards.
- 47 tests across all six pass-rate suites pass together.
- `ruff check app/ tests/` (CI's scope) clean. The 8 findings in `scripts/` are
  pre-existing — the same 4 appear in `seed_data.py` on `main`.

## Not done

The seeded rows already in databases are **not** corrected. This fixes the
generator; existing local/demo data keeps its wrong `pass_rate` until reseeded.
A backfill would need to be a migration, and it would rewrite data the owner may
be comparing against — that is a deliberate decision, not an oversight.
