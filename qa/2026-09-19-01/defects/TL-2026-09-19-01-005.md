# TL-2026-09-19-01-005 — The exported PDF publishes a pass rate without its basis

- Found by: JR-05 step 5 (export)
- Severity: **S3** (a number is unreadable on the surface most likely to be read alone) · Priority: P2
- Component: `backend/app/services/summary_report_pdf.py`
- Status: **FIXED** on `qa/jr05-summary-2026-09-19`

## Measured

`GET /api/v1/reports/summary/pdf?project_id=852a9cf9…&days=30` → HTTP 200,
`application/pdf`, 40,015 bytes, valid `%PDF-1.4`, 17 pages.

The export is **numerically faithful**. All thirteen published values appear:

```
total 129   passed 91   failed 28   skipped 9   broken 1   evaluated 120
pass 70.5%  fail 21.7%  skip 7.0%   broken 0.8%  weighted 75.8%
runs 213    flaky 74
```

But these strings were **all absent**: `basis`, `unique test`, `unique_tests`,
`per test execution`. The headline read:

```
Pass %      Weighted pass %
70.5%       75.8%
```

Two different pass rates, side by side, with nothing saying why they differ or
what either divides by.

The page does not have this problem — `SummaryReportPage.tsx:335-338` renders the
Pass % tile with `sub = "{pass_rate_basis_label} · weighted {x}%"`, i.e. "per
unique test · weighted 75.8%".

## Why the PDF is the worst place to drop it

The PDF is the **detached** surface. It is emailed, attached to compliance packs
and shared reports, and read with no application beside it to supply the missing
caption. Every other surface that shows this number has the app around it.

`tests/regression/test_pass_rate_basis_is_published.py` already pins this one
layer down — "a computed field must survive its response_model" — and exists
because a bare pass rate misled a reader before. The field survived the API and
then died at the export.

## Fix

A one-sentence caption under the headline table, driven by the payload:

```
Pass % is measured per unique test. Weighted pass % divides by executed tests
only (passed + failed + broken), so skipped tests are excluded.
```

Additive only — no number moved, and the basis text comes from
`pass_rate_basis_label` rather than being hardcoded, so the other basis this
product defines ("per test execution") reports itself correctly. An empty or
missing label degrades to the previous output rather than raising: an export that
500s would be worse than one missing a caption.

## Tests — `tests/regression/test_summary_pdf_states_pass_rate_basis.py`, 6 tests

- the PDF still renders and still starts with `%PDF-`
- the basis is stated
- it explains why the two rates differ ("skipped tests are excluded",
  "passed + failed + broken")
- **every number is still present** — a caption that displaced a value would be a
  worse defect than the one being fixed
- a *different* basis reports itself, so the wording is not hardcoded
- a missing label does not break the export

The text extractor normalises whitespace, and that is not cosmetic: the generated
PDF wraps the sentence across a line break between "are" and "excluded", and a
naive substring check reported a **false negative against a correct PDF** on the
first run of this very assertion.
