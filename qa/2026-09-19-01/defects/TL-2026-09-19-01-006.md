# TL-2026-09-19-01-006 — Release-gate hard-cap docs contradict the classifier

- Found by: JR-06 (band + hard-cap semantics)
- Severity: **S3** (documentation, on the release-gate policy surface) · Priority: P2
- Component: `backend/app/models/schemas.py` — `PolicyHardCaps`
- Status: **FIXED** on `qa/jr06-release-gate-2026-09-19`

## What is NOT wrong

The classifier's asymmetric treatment of `0` is **deliberate, reasoned and
tested**. `tests/test_classify_with_policy.py` pins it and explains why: *"P0 and
flaky treat 0 differently because P0=0 is the only intent the user actually
wants. `flaky=0` would over-fire on real projects."*

I measured the behaviour first and nearly filed it as an S2 false GO against the
fail-closed mechanism:

```
caps = {max_p0_defects: 0, max_flaky_count: 0, max_new_failures_24h: 0}
100% pass, 25 flaky, 50 new failures -> green GO, no downgrades
100% pass, 1 P0                      -> red   NO_GO, [p0_defects:1>0]
max_flaky_count=1, 25 flaky          -> red   NO_GO, [flaky:25>1]
```

Tightening the flaky cap from 1 to 0 turns enforcement off — which looks exactly
like a defect until you find the test that intends it. Checking before filing is
the whole point; "fixing" this would have broken correct behaviour and a passing
test.

## What IS wrong

That reasoning existed **only in a test docstring**. `PolicyHardCaps` is a
Pydantic model, so its docstring and field descriptions are the OpenAPI
documentation a policy author reads, and it said two things the code does not do:

| Documented | Actual |
|---|---|
| "`None` (or 0 where `ge=0`) disables the cap" | false for `max_p0_defects`: 0 is the **strictest** setting |
| "exceeding it downgrades the resolved band by one step" | false: a breach **pins the band to red** and forces NO_GO |

Both misread dangerously on a release gate:

- an author sets `max_p0_defects=0` believing they switched P0 blocking **off**,
  and has switched it to maximum;
- a breach reads as a nudge rather than a block. The implementation comment is
  explicit that one-step was abandoned because "yellow still mapped to GO — so an
  otherwise-green run with open P0 defects still shipped GO, which made the
  'hard cap' advisory at best".

All three fields also shared one description shape — "X allowed before
downgrade" — which conveys the P0 semantics and the *opposite* of the flaky and
new-failure semantics.

## Fix

Documentation only. **No behaviour change; every existing policy test still
passes.**

- The class docstring now states that a breach pins to red and forces NO_GO, and
  that zero does not mean the same thing for every cap — refusing to summarise
  the asymmetry in one blanket sentence, since that is what went wrong before.
- Each field states its own zero behaviour, and the two disable-able caps name
  the value that does what the author probably meant ("set 1 to block on the
  first flaky test").

## Tests — `tests/regression/test_hard_cap_docs_match_behaviour.py`, 15 tests

The tests assert the documentation against **live classifier behaviour** rather
than against fixed strings: each case calls `classify_with_policy`, asserts what
actually happens, and then asserts the description says that. Docs and code
cannot drift apart again without failing here.

Also pins the band edges (99.0 → green, 98.99 → yellow, 95.0 → yellow, 94.99 →
orange, 90.0 → orange, 89.99 → red), recorded because "is there an off-by-one at
a band edge" is the question JR-06 asks and the answer is **no**.

  **2 guards fail.**
- 84 tests pass across the hard-cap, classifier and release-gate suites, with the
