# TL-2026-09-19-01-007 — A written release decision is not always announced

- Found by: JR-06 (`release.decided` emission)
- Severity: **S3** · Priority: P2 · **Owner decision required — not fixed**
- Component: `backend/app/agents/decision_report_critic_agent.py` (emission point),
  `backend/app/services/webhook_service.py` (`SUPPORTED_EVENTS` description)
- Status: **REPORTED**, behaviour deliberately left unchanged

## What is NOT wrong

The 2026-09-12 "declaration is not emission" gap — `SUPPORTED_EVENTS` offering
`release.decided` while nothing ever sent it — **is genuinely closed**.
`app/services/release_decision_webhook.py` exists, has two production call sites,
and all three are pinned by tests. Verified by mutation, not by reading:

| Mutation | Result |
|---|---|
| M1 — emitter returns a plausible count but stages nothing | **7 tests fail** |
| M2 — critic imports `emit_release_decided`, never calls it (the original defect shape) | **1 test fails** (`test_published_report_emits_release_webhook_with_exact_evidence`) |
| M3 — override route never publishes | **1 test fails** (`test_an_override_is_announced_after_the_route_commits`) |

M1's kill matters most: the tests assert a delivery was *staged*, not that the
function returned a number.

Note that `test_release_decided_webhook.py` (22 tests) did **not** catch M2 — only
the critic's own suite did. Neither file alone covers the wiring.

## What IS wrong

**The decision is written by one agent and announced by a different, later one.**

- `release_risk_agent._persist_decision` constructs and **commits** the
  `ReleaseDecision` (`app/agents/release_risk_agent.py:621`). It emits nothing.
- `emit_release_decided(trigger="agent")` is called only from
  `DecisionReportCriticAgent._persist`, which runs only when
  `verification.status == "passed"`. On the failure branch the critic calls
  `_persist_failure`, which contains **no emission** (`emit_release_decided`
  appears exactly twice in that module: the import and the one call, both on the
  success path).

So when the terminal report fails verification, the release decision still
exists, is still committed, and is still what `GET /api/v1/release-readiness/{run_id}`
returns to the UI and to CI — but no subscriber is ever told.

The harmful shape is not a missing first event; it is a **stale** one. The
`release_decisions` row is keyed by `test_run_id` and *updated* on a re-run. If a
later pipeline revises the recommendation and that pipeline's critic fails, the
subscriber keeps the previous value while the UI shows the new one.

## Measured on the live deployment (homelab, read-only)

Not theoretical. Stage outcomes across all pipelines:

```
release_risk             completed 236   failed  0   skipped 13   pending 5
decision_report_critic   completed 160   failed 56   skipped 13   pending 1
```

The writer never failed. The only agent-path emitter failed 56 times.

Joining decisions to their own pipeline's critic stage:

| critic stage for that decision's pipeline | decisions |
|---|---|
| completed | 158 |
| **failed** | **20** |
| no pipeline row (seeded demo rows — excluded) | 22 |

**20 of the 178 decisions that have a real pipeline — 11% — would never have been
announced.** Their stage error is verbatim the source's own string,
`terminal decision verification failed closed`. Example run
`8dc94ced-cac9-4f49-9418-654b000e5d6b`, CONDITIONAL_GO, risk 41.

## How it got this way — a relocation, not an oversight

**Added 2026-09-19, from the stale `fix/release-decided-webhook-emission`
worktree.** This is not how the feature shipped.

PR #67 (`a281a9ce`, 2026-09-13) emitted `release.decided` **from the writer** —
in `release_risk_agent._persist_decision`, immediately after `await db.commit()`:

```python
# Outbound ``release.decided``. It runs after the commit above so a
# subscriber never hears of a decision that rolled back.
await emit_release_decided(test_run_id, trigger=TRIGGER_AGENT)
```

That design has **no gap**: every committed decision announces itself,
regardless of what any later stage does. `main` carried it for four days.

Two commits on 2026-09-17 moved it:

| Commit | Effect |
|---|---|
| `057826a7` "fix(review): bind queued delivery to exact evidence" | added emission to the critic |
| `21f1e98f` "fix(review): bind publication to immutable source" | **removed it from the writer** |

So the 11% is a **regression introduced by a deliberate relocation**, not an
oversight in the original design. The E8.4 work bound publication to the
immutable, verified report subject so that authority follows pipeline + evidence
hash — a real and defensible reason.

But the *consequence* was almost certainly not priced. The goal was authority
binding; "a decision whose report fails verification is never announced at all"
reads as a side effect, not a decision. Nothing in either commit message, the
CHANGELOG, or the code comments acknowledges it.

## The documentation half is unambiguous — and now doubly stale

Three surfaces describe where this event fires. The 2026-09-17 move updated one
of them.

**Correct** — the module docstring in `release_decision_webhook.py` names
``DecisionReportCriticAgent._persist``. Whoever moved the emission knew exactly
what they were doing here.

**Stale (1)** — `GET /api/v1/webhooks/events` serves `SUPPORTED_EVENTS`:

> "Fired when a release decision is written: by the release-risk agent at the end
> of a deep investigation, or by a QA lead's override."

A write by the release-risk agent is **not** sufficient — that is precisely the
11% above.

**Stale (2)** — `CHANGELOG.md:1177`, the "Where it fires" contract from the
2026-09-13 entry, states it outright:

> "There are two writes of a release decision, and **both emit** after their
> transaction commits: the release-risk agent persists a decision at the end of a
> deep run (`trigger: "agent"`) [...]"

True when written. False since 2026-09-17. This is the third instance this week
of the same pattern — accurate internal docstring, stale public contract — after
TL-2026-09-19-01-006 and the `PolicyPassRateBands` claim found beside it.

## Why this is not fixed here

The history above narrows this but does not close it. Binding
publication to the immutable report was deliberate, so option 1 is now the
likelier reading — but "we chose to bind authority to a verified report" is not
the same statement as "we chose that 11% of committed decisions go unannounced",
and only the owner can say whether the second follows from the first.

1. **Intended** — then `SUPPORTED_EVENTS` and `CHANGELOG.md:1177` must both say a
   decision is announced when its report is *published*, not when it is written,
   and the 11% becomes a documented property of the gate.
2. **Not intended** — then the failure path needs an emission, probably under a
   distinct trigger without the evidence hash, since by definition there is no
   verified bundle to reference.

Those produce opposite documentation, which is why guessing would repeat the
mistake that produced 006. **Owner decision.** No behaviour changed.

Note that **the CHANGELOG line is wrong under either outcome** and can be
corrected independently of the decision.

## Also unmeasured, and why

Live emission was never observed end to end. `outbound_webhooks` is
`enabled_global = false` on homelab with **zero** subscriptions and **zero**
`webhook_deliveries` rows ever, so `_post_allowed()` short-circuits
`emit_release_decided` to 0 before any work. That is correct opt-in behaviour,
not a defect — but it means the event has never actually fired on a real
deployment. Enabling the flag and adding a subscriber are cluster writes, which
this session is not permitted to perform.

**No test stages a `release.decided` delivery against a real PostgreSQL.** The
22-test suite drives a fake session that "plays PostgreSQL" (it does compile and
read back the real `INSERT ... ON CONFLICT`, so the SQL is real; the database is
not). The only real-Postgres webhook staging test,
`tests/integration/test_run_downstream_outbox_postgres.py`, covers
`run.completed` — including the 1-then-0 idempotency proof — and CI does provide
a real DSN for it. `emit_event` is shared machinery, so the mechanism is proven;
`release.decided`'s own `delivery_scope` key shape is not.
