# TL-2026-08-29-02-001 — Parent checkout history collected for a non-Git path

- Priority: P1
- Status: **FIXED** on `main` (`d2bbad24`); **regression test added 2026-09-21**.
  This line used to read "verified by regression suite", which was not true.
  The fix commit added no test, and the only coverage,
  `test_non_git_directory_returns_none`, uses a directory OUTSIDE any checkout,
  where git fails with or without the fix — it passed with the fix switched
  off. `test_a_plain_directory_inside_a_checkout_does_not_report_the_parents_history`
  now nests the directory inside a real checkout, with a positive control
  proving the parent has history to leak. It fails when the guard is removed
  from either copy (SDK and CLI), each independently.
- Affected areas: `client/commit_range.py`, `cli/testlookup_cli/commit_range.py`

## Reproduction

1. Create a plain directory inside a Git checkout.
2. Call `collect_commit_range(env={}, repo_path=<plain-directory>)`.
3. Observe that `git -C <plain-directory> rev-parse HEAD` walks to the parent checkout and returns the parent repository's commit range.

The shared regression test `test_non_git_directory_returns_none` failed for both implementations. The diagnostic contract test also failed because the outcome was reported as successful `git_fallback` collection instead of `not_a_git_checkout`.

## Impact

Callers supplying an explicit repository path could attach unrelated parent-repository commits to an ingest payload. This corrupts commit attribution and can influence downstream test-impact analysis.

## Fix

Before resolving `HEAD`, both collectors now require an explicitly supplied `repo_path` to be an existing directory containing its own `.git` metadata. This preserves normal `repo_path=None` behavior and allows Git worktree roots, where `.git` is a file.
