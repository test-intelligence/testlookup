Section 1System and architecture assessment

What exists, how it is wired, and where the structure works against the product's own goals. Every claim below is anchored to a file and line in backend/app.

1.1  The thesis in one paragraph

The 2026-08-11 review asked for a canonical evidence bundle, a terminal synthesis stage after all specialists, typed claims, and an independent critic. All four shipped. DecisionReportAgent now recomputes nothing with an LLM — it projects deterministic facts and the critic re-derives the authoritative report and compares it field by field, fingerprint included (decision_report_critic_agent.py:172-310). That is the right architecture, and it is genuinely rare.

The consequence is that the remaining risk has moved. It is no longer “is the report structurally sound?” It is “is the content inside the structure any good, and would we know if it got worse?” The prior PRD wrote down ten quality targets — citation validity above 98%, unsupported claims below 1%, p50 report latency under 90 seconds, calibration error at target. Nothing in the running system measures a single one of them, and one of them (citation validity) cannot be satisfied by the current implementation at all. Section 2 covers why.

1.3  Orchestration: correct, but paying for it in wall-clock

The deep graph is a 19-node chain in which only one fan-out survives (ingestion into anomaly plus analysis). Four read-only domain specialists — contract_validation, log_intelligence, regression_watchman, change_ownership — declare no dependency on each other in the capability registry, yet run strictly one after another (workflow.py:995-1000).

The comment at workflow.py:944-963 explains why, and it is worth reading before anyone “fixes” this: a previous fan-in placed clustering three hops from ingestion while the other branches were one hop, so LangGraph scheduled summary in two supersteps. On the homelab, 2026-08-16, that made the whole specialist chain run twice and the decision-report verification log both a pass and a fail 464 ms apart, with the failure winning. Serializing was the correct emergency response. It is not the correct steady state — the Investigator already demonstrates the right pattern with reducer-keyed parallel nodes (investigator/state.py:47-56), and the fix is an explicit barrier node rather than depth-matched edges.

1.4  Context construction is the weakest layer

Four independent problems compound here, and together they are the most likely cause of any perceived “the AI is vague” complaint.

  • No shared evidence bundle upstream. The capability registry declares inputs="RunEvidenceBundleV1" for exactly ten stages, but the bundle is only ever built at the terminal decision stage (decision_report_agent.py:296). Every specialist re-queries Postgres for the same run — 25 query sites across seven specialists (anomaly 9, regression-watchman 6, flaky 3, ownership 3, release-risk 2, health 1, clustering 1), opening 11 separate sessions.
  • Ollama's context window is never set. llm_factory.py:176-182 passes num_predict but never num_ctx. Ollama silently truncates over-length prompts server-side, so evidence — and on the ReAct path, the tool instructions themselves — can vanish with no error, no metric, and no log line.
  • Token budgeting is len(text)/4 (resilience.py:183-188), not a tokenizer. Stack traces and structured logs tokenize far worse than 4 characters per token, so the estimate skews optimistic exactly where the payload is largest.
  • The summary sends the same context four times. summary_agent.py:504-547 builds one context string and issues four sequential calls with it — executive summary, incident view, evidence pack, action plan — each truncated to LLM_MAX_TOKENS - 1500.

1.5  Model layer: strong isolation, no structure

Eight providers behind one factory, with a BudgetedLLM wrapper that checks the admission decision at the invocation boundary, sanitizes arguments through the privacy policy, and records observed token usage back into the pipeline budget context (llm_factory.py:19-107). AI_OFFLINE_MODE is a hard egress ceiling. This part is done well.

What is absent is any use of structured output. BudgetedLLM.with_structured_output exists at line 101 and is never called anywhere in the codebase. Every structured result in the system is produced by asking a model for JSON in prose, then recovering it with fence-stripping and a balanced-brace regex (llm_json_parser.py), or — on the main analysis path — by LangChain's legacy string-parsing ReAct agent with handle_parsing_errors=True (services/agent.py:194-205). Parse failures are handled gracefully, which is why this has never looked like an outage; they are also charged a full retry (analysis_agent.py:521-522) and otherwise degrade to schema defaults.

One model tier serves everything. qwen2.5:7b at temperature 0.1 classifies a one-line assertion failure and synthesizes a release decision.

The gap worth naming: the organization's own written knowledge never reaches failure triage. Runbooks, ADRs, incident write-ups and service ownership docs are ingested, chunked, embedded and gated behind KNOWLEDGE_RAG_ENABLED — and then used exclusively to generate test cases. The agent explaining why a payment test failed at 3 a.m. cannot read the payment service's runbook.

1.7  What is already excellent

A review that only lists problems will get the wrong things changed. These are load-bearing and should survive every recommendation below.

Prompt registry with an enforced ratchet

Every prompt is versioned, hash-pinned in a manifest, and a CI gate fails on drift or a missing eval attestation. Prompts cannot ship silently.

Deterministic report + independent critic

The decision report computes facts without an LLM; the critic recomputes and compares fifteen checks including an evidence fingerprint.

Honest confidence documentation

confidence_gate.py states in its own docstring that the numbers are self-declared, not calibrated, and forbids calling the threshold calibrated in UI copy.

Budget reserve and settle

Stages reserve budget before invocation and settle after, with durable pending receipts and a reaper for failed settlements.

Tenant-scoped caches

Semantic cache collections are per project by construction, and the recall tool takes identity from a server-side ContextVar, never from model output.

Full-fidelity stage telemetry

Decision logs, OTEL spans with fallback and route attributes, per-stage tokens and cost in Postgres, immutable events in Mongo.

Section 4AI output quality

Accuracy, grounding, and multi-agent coherence. The structural honesty work is done; this is about the content that flows through it.

4.1  Replace verbatim citation matching with an evidence-ID contract

This is the single highest-value quality change in the document, because it converts an unverifiable narrative into a checkable one.

  1. Number the evidence the model is given: each item in the context carries a stable ev_id already available from the authorized artifact resolver.
  2. Require the model to emit claims as objects with an evidence_ids array — enforced by structured output (O-1), not by instruction.
  3. Validate server-side: drop or demote any claim whose ids do not resolve to authorized artifacts for this run. This mirrors what the decision critic already does for typed claims, extended to prose.
  4. Report citation coverage and unsupported-claim rate as first-class metrics per report version.

The decision report already refuses to publish on evidence-authorization errors; this brings the LLM narrative under the same rule instead of trusting a 40-character string match.

Revision 5 — the contract is not the binding constraint

All four steps above shipped in #792, and citations still measured 0 of 30 on the homelab. The reason is not the model declining the contract — it is that 99.94% of analyses produce no evidence at all (F-17), so the catalogue handed to the model is empty.

Fixing the citation mechanism was the wrong end of the chain to start from. Evidence production is the prerequisite: the rules engine runs 87% of analyses and invokes no tools, and the LLM path's fast classifier returns before the ReAct loop that would gather any. Until that changes, G.2 is a correct mechanism with nothing to carry.

4.2  Extend the critic to the narrative

evaluate_decision_report runs fifteen deterministic checks and none of them look at generated prose. Add three that can be computed without a second model: numeric consistency (every number in the narrative must appear in the metric snapshot), entity validity (every named test, suite or service must exist in the run), and verdict agreement (the narrative's implied release stance must match the deterministic decision). All three are cheap, local, and catch the failure modes that actually embarrass a report.

4.3  Make the semantic cache degrade, not impersonate

A near-match at 0.85 similarity is evidence about a category, not a root cause for this test. Recommended behavior: reuse the category and confidence band, discard the narrative and recommended actions, mark the result cache_derived with the similarity attached, and scale confidence by distance. The tenant scoping is already correct; this is about not passing off one failure's story as another's.

4.4  Give triage access to the knowledge base

Wire rag_retrieval_service into the analysis path as a seventh ReAct tool and as pre-retrieved context for the fast classifier, subject to the same knowledge_rag flag and redaction. A runbook that says “connection reset here means the payment sandbox recycles at 03:00” converts an INFRASTRUCTURE / unknown verdict into a specific, actionable one. The retrieval, chunking, embedding, redaction and faithfulness machinery all exist; only the wiring to triage is missing.

4.5  Calibrate confidence instead of declaring it

The system is admirably honest that its confidence numbers are self-declared. The next step is to stop needing the disclaimer: with human corrections, Jira resolutions and fix outcomes already stored as labels, fit a per-category reliability curve (isotonic or Platt) offline, publish it as a versioned artifact, and map raw scores through it. Then ai_confidence_threshold becomes a genuine risk dial and expected calibration error becomes a gate-able metric — the harness that computes it already exists in agent_eval_harness.py and is currently only exercised by tests.

Section 5Self-improving system design

The honest current state: every loop in this system requires a human to close it, and the one automated loop is disabled by default and forbidden by the product's own offline posture.

The structural problem

Labels flow to the ML classifier and the fine-tune corpus. auto resolves ML → LLM → rules, so a trained classifier is preferred once it exists — but it only exists after 200 labeled samples. Below that threshold the LLM runs and learns nothing, which is precisely the period when a new project's answers are worst and its users are deciding whether to trust the product. Fine-tuning, the one path that would improve the LLM directly, is off by default, OpenAI-only, and refused when AI_OFFLINE_MODE is true — which is the default.

5.2  A flywheel that works offline

Four layers, each shippable on its own, none requiring a cloud provider or model training.

Proposed learning architecture
LayerWhat it doesNew capability
1 · Capture Add the signals already produced but not harvested: the Fixer's sandbox validation result (a re-run that passes is ground truth about the root cause, independent of whether a human merged the PR), quarantine reversals, and re-run outcomes on unchanged code. The first labels that need no human at all
2 · Measure A nightly eval job over the golden corpus plus recent labeled analyses, writing an AIEvalRun per task type with accuracy, macro F1, calibration error, citation coverage and contradiction rate. Drift detection compares to the active baseline and opens an alert, not a silent log line. Continuous quality signal (fixes F-11)
3 · Adapt without training Three mechanisms, in ascending order of ambition: (a) retrieval-augmented exemplars — inject the k nearest confirmed corrections as few-shot examples into the fast classifier, which is zero-shot today; (b) threshold auto-tuning — propose ai_confidence_threshold and SEMANTIC_SIMILARITY_THRESHOLD values from the measured precision curve; (c) prompt candidates — generate variants offline, score them through the existing eval gate, and require the same manifest attestation to promote. Improves the LLM path in an air-gapped install
4 · Train When the human-label corpus passes the existing thresholds, run local distillation (LoRA against the Ollama-hosted base) rather than a cloud fine-tune. Promotion stays behind eval_gate_service and the model registry, which already support candidate versus active comparison. Makes fine-tuning viable under the default posture

Governance rides the mechanism that already exists: every adaptation is a proposal, proposals run in shadow until they beat the baseline over two consecutive eval cycles, and promotion writes an audit row. That is precisely the shadow-to-active discipline the agentic layer uses for actions — extended from what the system does to what the system becomes.
