# Adversarial review — AGENTIC_OPENAPI_ARCHITECTURE_2026_09.md (sections 1,2,5,6,7)

- [HIGH] §7.2/7.3 lease-reaper race with in-graph retries: the doc proposes the reaper reclaims a `running` row whose `lease_expires_at` passed and moves it to `retry_wait`/`failed`, re-enqueuing a new attempt — but the CURRENT worker process is not guaranteed dead, only slow to heartbeat (GC pause, a single long LLM call inside `_make_checkpointed_node` that doesn't heartbeat until the stage returns, per §7.3 "heartbeat every 30s from mark_stage_running/done" — that's a heartbeat at STAGE boundaries, not sub-stage). A stage whose single LLM call runs longer than `2*heartbeat` (60s) with no intra-stage heartbeat looks lease-expired while still legitimately running -> reaper starts attempt 2 concurrently with attempt 1 still writing to the same `pipeline_run_id`'s checkpoints (`_checkpoint_stage` in workflow.py:970) and stage rows (`_mark_stage_executed`/`_mark_stage_failed`) with no fencing token compared. This is double execution, not just double dispatch: two Celery workers both call mutating tools (triage/defect_commander) for the same run. -> Fix: fence writes with the lease token (a `lease_id`/`fencing_token` column checked with a WHERE clause on every stage write, not just on state-machine transitions), and heartbeat from inside long tool/LLM calls (a background heartbeat task per stage), not only at stage start/end.

- [HIGH] §7.5 saga: "Retries skip actions already `applied` (idempotency via ledger)" is asserted but the resume/retry path in workflow.py `resume_pipeline` (line ~1288) restores completed stages from `_checkpoint_stages` and skips re-running the *stage*, not the individual tool calls inside a stage. If `triage`/`defect_commander` create a Jira ticket, then the STAGE fails partway through a multi-tool loop (e.g. after ticket creation but before writing the stage's own checkpoint), the checkpoint for that stage was never written (checkpoint write is at the END of `_make_checkpointed_node`, workflow.py:1637-1643, gated on success) — so a manual/automatic retry re-runs the WHOLE stage from scratch, including the tool call, unless the tool call itself consults the `AgentActionLedger` before acting. The doc says the ledger check happens "before the call" but never specifies that the *stage entry point* (not just the tool wrapper) queries the ledger for `state=applied` rows scoped to `(run_id, tool, idempotency_key)` before re-invoking. If that check lives inside the tool function and the stage's early logic (e.g. "which tickets need creating") is computed from state that doesn't yet reflect the ledger, you can get a second ticket for the same failure with a different dedup key derived from a re-run because `attempt` changed. -> Fix: specify that idempotency keys for mutating tool calls are derived from `(run_id, tool, subject_id)` — NOT `(run_id, attempt, tool)` — and that the ledger lookup happens as the first line of the stage node, before any planning logic runs, not only inside the tool wrapper.

- [HIGH] §7.4 "Celery's own `self.retry` is no longer used for pipelines... the new path releases the dedup lock before scheduling and the scheduled task re-acquires it" — but this contradicts the existing dedup key design read in worker/tasks.py:1911 (`testlookup:dedup:pipeline:{test_run_id}:{workflow_type}`, TTL 7200s, acquired for the whole 2-hour window `_is_duplicate(... ttl=7200 ...)`). If the new `retry_wait` scheduling path releases the dedup lock immediately so the rescheduled `apply_async(countdown=delay)` can re-acquire it, there is now a window (between release and the scheduled task firing) during which ANY other trigger for the same `test_run_id`/`workflow_type` — e.g. a user hitting "Retry" via the new `POST .../retry` endpoint in E7.4, or a webhook re-delivery, or another CI run reporting the same build_number — passes the duplicate check and starts a SECOND concurrent run while the first is sitting in `retry_wait` waiting for its `next_retry_at`. The memory note the doc itself cites ("a dedup lock can silence its own retry") describes the opposite failure mode (retry silently skipped); the fix as specified reintroduces the double-execution failure mode instead of fixing both. -> Fix: don't fully release the dedup lock on transition to `retry_wait` — extend its TTL to `next_retry_at + grace` and have the state machine (not the lock) be the sole gate on whether a NEW trigger is accepted; the scheduled retry task should re-enter through the same run_id/attempt, not re-acquire a fresh dedup lock.

- [MED] §7.2 transition table: `running --cancel_requested--> failed` is listed as a single-arrow transition, but the code's existing `cancel_requested` mechanism (referenced but not shown) is almost certainly a flag checked cooperatively between stages, i.e. checked in `_make_checkpointed_node` before or after `original_node` runs. The table doesn't specify WHERE this check happens relative to `retry_wait`. Consider the race: a stage fails with a retryable error the same tick a user calls cancel. If the retryable-error branch and the cancel-check both fire (one in the exception handler after `original_node`, one in a pre-flight check next node), you get an ambiguous outcome depending on ordering: does the run land in `retry_wait` (scheduling a future re-entry) or `failed` (cancelled)? If `retry_wait` wins the race, the scheduled retry later re-enters a run the user explicitly cancelled, silently resurrecting mutating-tool proposals the user tried to stop. -> Fix: cancellation must be checked and consumed atomically as part of the SAME transaction that decides retry_wait vs failed (e.g. `UPDATE ... SET status=... WHERE status='running' AND cancel_requested=false RETURNING id`), not as a separate cooperative flag checked at an arbitrary point.

Meanwhile the OpenAPI status enum (§3.3, AgentInvocation) lists `passed` as one of exactly 4 public values with no fifth "not applicable" state — so any client polling for `passed` on a `review_policy=none` workflow (e.g. an OpenAPI-exposed cheap deterministic agent like `flaky_sentinel` that never needs human review, per §5.2's "closed-form metrics" list) will poll forever, since that agent can only reach `completed`. -> Fix: either (a) define `passed` = `completed` immediately when `review_policy=none` (auto-pass, no gate), or (b) explicitly state such capabilities never report `passed`, only `completed`, and document that a client must not require `passed` from a sync-eligible/no-review agent. As written, the four-state vocabulary is not uniformly well-defined across agents.

- [MED] §6.2 escalation loop: "`retry` re-runs the reviewed steps with `tier=llm` (one loop iteration, bounded by `loops[].max_iterations`)". `loops[].max_iterations` is a WORKFLOW-DEFINITION-level construct (§4.4, tied to a specific named loop edge like `review -> rca`). But the built-in reviewer (`agent.reviewer.v1`) is described in §6.2 as attachable generically ("Attachable at any point in a user workflow") and the escalation described in §5.3 is a SEPARATE bounded mechanism (`cfg.model.escalation.max_escalations`) that also mutates `tier` from slm to llm. These are two independently-bounded loops (workflow `max_iterations` vs escalation `max_escalations`) that both fire on essentially the same trigger (low confidence / failed validation) for the SAME step. Nothing in the doc says these two counters are unified or that one accounts for the other — worst case, a step can escalate slm->llm (1 model escalation), still fail review, loop back via `max_iterations=2` and re-run at `llm` tier again (now consuming a SECOND llm call that the model-escalation budget thought was already "used up"), and the retry counts against neither the run's `attempt` nor a shared ceiling — only against the workflow loop's own counter. Combined with per-capability LLM cost budgets (§2.1 `llm_cost_budget`), this is a plausible cost/latency blowup path that the "bounded" language implies is impossible but the design doesn't actually cross-check. -> Fix: state explicitly that `loops[].max_iterations` and `escalation.max_escalations` share one budget counter per step-invocation (e.g. total LLM calls for step X across all loop+escalation combined must not exceed N), and add that ceiling to the `StepContext`/`RetryPolicy` shared object rather than leaving it split across two config surfaces.

- [MED] §6.3 anti-collusion: "Reviewer's own output is deterministic-checked... but never LLM-reviewed — one level of review, not a tower." Good in principle, but §5.2 matrix row for `decision_report_critic, reviewer` says tier is "deterministic checks; llm second-model check optional". If `second_model_check=true`, the reviewer's OWN verdict-producing call ("does this conclusion follow...") IS an LLM call, and its OUTPUT (the `ReviewVerdictV1.verdict`) directly controls a state transition (`retry`/`reject`/`pass`) without being schema/grounding-checked the way generator outputs are (§6.2 family 1 explicitly targets "the step's contract" for GENERATED reports, and family 5's policy check is about mutating proposals, not about validating the reviewer's own confidence/verdict fields). So an LLM producing a malformed or overconfident `verdict` (e.g. hallucinating `"pass"` when its own listed `disagreements` are non-empty and severe) has no stated deterministic cross-check ("if disagreements contain a blocking severity item, verdict must not be pass") before the Supervisor acts on it. -> Fix: add an explicit deterministic invariant check on the reviewer's OWN output before the Supervisor consumes it (e.g. verdict=pass requires zero blocking-severity disagreements; contradiction -> treat as `reject` fail-closed), consistent with how `decision_report_critic` is praised elsewhere in the doc for being "bounded, deterministic, fail-closed."

- [LOW] §5.3 escalation algorithm pseudocode: `if budget.remaining(state) < cap.cost_usd: return ModelChoice("deterministic", ...)` runs BEFORE checking `tier == "deterministic"`, which is fine, but the escalation block below it (checked "inside the worker, after a call") doesn't re-check budget before escalating slm->llm. An in-flight escalation triggered by `confidence < on_confidence_below` can push the run over its `budget.max_cost_usd` even though the pre-call check passed for the (cheaper) slm call. The doc's own §5.2 states budget is supposed to be "a routing input, not just a kill switch" — but the escalation path bypasses that input entirely. -> Fix: gate the escalation branch itself on `budget.remaining(state) >= cost_estimate(llm)` before upgrading tier, falling back to `cap.fallback` if insufficient, matching the pre-call precheck's own logic.

- [LOW] §2.1 / §7.3: BaseAgent's existing `mark_stage_running`/`mark_stage_done` hooks are stated to be "opt-in per BaseAgent subclass" per the comment already in `_make_checkpointed_node` (workflow.py:1621-1630: "three specialists plus the two plain cluster-investigation node functions never call it"). The proposed lease-heartbeat mechanism (§7.3) is built entirely on these same hooks ("a natural hook in BaseAgent"). Since the doc itself elsewhere documents that some existing stages skip these hooks, the new lease/heartbeat mechanism inherits the same gap: any stage that doesn't call mark_stage_running will never renew its lease and will always look stale to the reaper regardless of whether it's healthy, even on first execution. -> Fix: E7.3 should explicitly include auditing/fixing the "opt-in" hook gap identified in the current code comment before leases become the sole staleness signal (currently a soft UI-display issue; under the new design it becomes an incorrect reap-and-retry, i.e. correctness-critical rather than cosmetic).

- [LOW] §3.5 / router registration: the doc's own mitigation ("`agent_id` uses the pattern `^agent\.[a-z_]+\.v\d+$` so `/agents/pipelines/...` cannot collide") assumes FastAPI path resolution for `/agents/{agent_id}/invoke` vs `/agents/pipelines/trigger` is disambiguated by the regex constraint at match time — but FastAPI path converters only enforce type conversion (e.g. `{agent_id:path}` or a `Path(regex=...)`), and plain `{agent_id}` string params match ANY path segment including "pipelines" regardless of an application-level Pydantic regex validator that runs AFTER routing has already selected the endpoint. If `/agents/pipelines/trigger` is registered AFTER `/agents/{agent_id}/invoke` in a router that also handles single-segment vs two-segment paths ambiguously, or if some client hits `/agents/pipelines/invoke` (matching the agent_id pattern's `[a-z_]+` group as literally "pipelines"), the regex alone does not prevent the route match — it only makes such a call fail Pydantic validation with a confusing 422 instead of colliding silently. The doc treats this as solved ("cannot collide") when it only affects the FAILURE MODE of a benign path, not real route ordering, which the memory note it cites is actually about (register the specific router first). -> Fix: confirm route registration order explicitly in the story (E1.1/E1.2), not just the id pattern, per the project's own existing memory on this exact class of bug.

## Summary

The document is strong on paper (it correctly diagnoses today's `partial`/30-min-stale-window problems and proposes real fixes — leases, one retry-policy object, one state-machine writer), but three of its central reliability claims don't hold up against the concurrency model it's building on top of:

1. **Double execution is still possible**, via two independent paths: (a) the lease/heartbeat design heartbeats only at stage boundaries, so any long-running single stage looks lease-expired to the reaper while still legitimately executing, and reaped rows are re-enqueued with no fencing token to stop the original attempt's writes; (b) the "release dedup lock before scheduling retry_wait, reacquire on the scheduled task" fix for the existing "dedup lock silences retry" bug reopens a window where a fresh external trigger (manual retry endpoint, webhook redelivery) races the scheduled retry and starts a second concurrent run — trading one known bug for the opposite one.
2. **Saga/idempotency for mutating tools is asserted, not designed**: the ledger-before-call pattern is real, but retry-at-the-STAGE-granularity (not sub-stage/tool-call granularity) means a stage that fails after a ticket is created but before its checkpoint is written will re-run the whole stage; whether that re-run creates a duplicate ticket depends entirely on where the idempotency key is derived, which the doc never pins down.
3. **The four-status vocabulary is not uniformly well-defined**: `passed` is unreachable by its own stated AND-conditions for any workflow/agent with `review_policy=none` (which the doc's own §5.2 says applies to several deterministic, sync-eligible, "never needs review" capabilities) — a client polling for `passed` on those would poll forever. The `partial -> completed` backfill also silently breaks any existing `status == 'partial'` branch outside the DB layer with no audit step proposed to find them.

Secondary but real: the reviewer's two independent bounding mechanisms (workflow `max_iterations` and model `max_escalations`) are not unified into one budget, so a worst-case step can burn LLM calls beyond what either limit alone implies; the reviewer's own LLM-produced verdict has no deterministic sanity check before the Supervisor acts on it, which is inconsistent with the fail-closed standard the doc holds up elsewhere (`decision_report_critic`); and the cancel-vs-retryable-error race at the `running` state isn't given an atomic resolution, so a user's cancel can lose to a scheduled retry_wait and resurrect a run they explicitly stopped.

Recommend before this goes into planning: (1) add a fencing token to every stage write, checked against the current lease owner, not just to the state-machine's own transition writes; (2) specify tool-call idempotency keys as `(run_id, tool, subject_id)` and require the ledger check at stage entry, not just inside the tool wrapper; (3) resolve the `passed`-unreachable-under-review_policy=none case explicitly in §7.1's table; (4) unify escalation and loop budgets into one counter; (5) add the dedup-lock TTL-extension alternative instead of release-and-reacquire for retry_wait scheduling.
