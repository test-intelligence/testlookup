# Design decisions and trade-off analysis

[Documentation home](../README.md)

These decisions are reconstructed from implementation and explicit source comments. The trade-off evaluation is engineering analysis, not a claim that maintainers recorded a historical ADR choosing among every alternative.

| Implemented decision | Alternatives | Benefits | Costs, complexity and failure modes | Evolution guidance |
|---|---|---|---|---|
| Shared modular backend, separate API/worker processes | Microservices per domain; synchronous-only backend | Shared contracts and transactions; lower developer coordination cost; independently scale API/work queues | Large service/model surface and coupled deploys; imports/config must work in all process roles | Extract a service only with a clear ownership/scaling boundary and versioned protocol |
| PostgreSQL + Mongo + Redis + object storage | PostgreSQL/JSONB only; document-only database | Relational policy/state, flexible evidence, fast streams/queues, large payload offload | More operational burden, no cross-store transaction, recovery and retention complexity | Assign authoritative store per datum; keep durable intents/reconciliation and exercise restores |
| Asynchronous 202 ingestion | Parse/persist in request; direct DB writes by clients | Bounded HTTP latency, smoothing bursts, worker scaling | Acceptance can precede persistence; polling/status expiry; dispatch failure paths | Keep stable IDs, status/error contracts and queue health visible |
| Source-aware idempotency and worst-result duplicate collapse | Random new run per delivery; last-write-wins results | Retry-friendly integration; duplicate order cannot hide a failure | Identity metadata must be correct; equivalent test names collide by design | Test duplicate and concurrent first delivery with production DB constraints |
| Redis Streams and per-process fan-out | Direct in-memory broadcast; one socket consumer | Multi-process delivery, ordered replay opportunities, scalable ingestion | Pending entries, buffers and fan-out retention need recovery; memory is shared with critical services | Preserve ordering/cutover contracts and monitor lag/eviction |
| Durable outboxes, leases and fencing | Best-effort enqueue; broker exactly-once assumptions | Recover committed work after failures; reject stale worker writes | More state/reconciliation code and additional DB load | Keep operations idempotent; test crashes at commit/dispatch boundaries |
| Bounded graph workflows and isolated child queue | One long prompt; unbounded autonomous agents | Explicit capabilities, per-stage evidence, concurrency limits, auditable decisions | Graph/checkpoint compatibility and parent-child coordination are complex; slow models dominate tail latency | Version/freeze behavior and verify resume authority; never let children starve behind waiting parents |
| Rules/ML/LLM routing | LLM-only; rules-only | Core usefulness without cloud access; cost/latency/availability fallbacks | Outputs differ in strength; model availability and promotion affect behavior | Return provenance and evaluate actual production data; label degraded results |
| Frozen automatic retry; changed config creates manual rerun | Recompute policy on every retry; reuse all checkpoints | Reproducible attempts and clear authority history | More hashes/version checks; reruns spend compute | Include all behavior-affecting inputs; preserve `rerun_of` links |
| Human report review plus distribution policy | Immediate publication; mandatory global approval on deploy | Separates generation from acceptance; observable rollout before enforcement | Default observation does not block; downstream consumers must honor envelopes | Roll out intentionally, test every export/webhook/CLI/MCP consumer |
| Deterministic release policy with append-only decisions | LLM-only verdict; overwrite a current row | Explainability, replay, evidence floor and audit history | Association/denominator correctness is difficult; row ordering matters | Version policy snapshots and test stale overrides/concurrent recomputation |
| Per-project quota and memory admission gates | Per-user limits; no admission gate; hard fail-closed | Noisy-project isolation and cheap fixed-window counters | Boundary bursts; admission probes can fail open on Redis errors | Align quotas with capacity and alerts; do not market them as hard safety ceilings |
| Local/private AI egress ceiling | Cloud-only; arbitrary configured URLs | Local deployment and data-residency controls including connection-time DNS pinning | Must provision weights locally; private-network permission is broader than one host | Combine application policy with deployment network boundaries and connector review |
| Feature flags with project/role/rollout filters | Build-time switches; separate forks | Gradual rollout with audit, one codebase | Legacy facade has different defaults; cache/commit order can affect observation | Use the modern scoped service; invalidate after commit and test authority-sensitive paths |
| React SPA with lazy routes and API types | Server-rendered pages; generated client-only UI | Rich triage, live views and reusable components; static frontend deploy | TS/backend drift and stale chunks; client controls are not authorization | Keep transport centralized, contract tests meaningful and server guards authoritative |

## Principles and patterns

The code favors explicit domain state machines, Pydantic contracts, dependency-injected access checks, adapter-based storage/connectors, append-only evidence/decision history, bounded retries and per-stage provenance. Examples are [workflow state](../../backend/app/services/workflow_run_state.py), [distribution policy](../../backend/app/services/report_distribution_policy.py), [run outbox](../../backend/app/services/run_downstream_outbox.py), [release decisions](../../backend/app/services/release_gate_decision_service.py) and [storage](../../backend/app/db/storage.py).

Concrete patterns the implementation guards against include granting access based only on a client-supplied project ID, concurrently sharing one async SQL session, treating all-skipped runs as passed, allowing report downloads to bypass review policy, loading unbounded archives, and replaying checkpoints under changed authority. Existing tests/quality ratchets encode many of these lessons; their existence is not proof that every future path is covered.

## Constraints and future improvements

Preserve existing API/state vocabulary unless versioning it deliberately. Keep the data stores, broker and worker topology in the capacity model. Prefer complete response models where APIs currently return unstructured dicts. Consolidate documentation entrypoints and automate drift checks. Profile actual workloads before changing databases, model tiers or concurrency. Future improvements are proposals, not currently guaranteed capabilities; see the [action register](../reviews/2026-09-18-action-register.md).
