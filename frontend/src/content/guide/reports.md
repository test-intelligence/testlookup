# Reports and outputs

Everything TestLookup can produce, what generates it, and where it lands: the run reports, the **Summary report** and **Value metrics** pages under **Reports**, exports and shared links.

## Deterministic vs generated, per report

The rule of thumb: **counts, scores and verdicts are computed; prose is generated.**

- A run summary's *numbers* are arithmetic; its *sentences* may be model-written.
- A release decision's *recommendation and risk score* are computed; the explanation around them may be generated.
- Flaky scores and cluster memberships involve **no** generative AI at all.

> **A summary is not always model-written.** When a stage falls back, its result carries `fallback_used: true` and a reason. The wording you are reading may be deterministic text produced without a model — the contract on the result tells you which, so a fallback is never presented as a model's judgement.

## The decision report is verified before publication

The deep pipeline ends with a critic that checks the report against the plan the pipeline was given — that every planned stage completed, that no unplanned stage ran, that routing rationales were recorded, and that anything producing output also produced a contract with its evidence.

> **Important.** If that verification fails, the report is **withheld** rather than published, and the run is marked `partial`. A missing report is a deliberate signal, not a glitch.

Every AI report is also a **review request** for a human. Until a QA lead accepts it, the report carries a **Draft: awaiting human review** banner; see [Your inbox and approvals](/docs/inbox#ai-reports).

## Freshness and regeneration

Reports reflect the run they were generated from. Re-running analysis produces a new result rather than editing the old one. A report you are reading is a record of a moment, not a live view.

## The summary report

**Reports → Summary** (`/reports/summary`, titled **Summary Report**) rolls up one project over a window (1, 7, 30 or 90 days); it asks you to pick a single project. It shows **Total tests**, **Pass %**, **Fail %**, **Broken %** and **Flaky**, a per-suite breakdown, the trend and the top failing tests.

Its **aggregation** setting decides what is counted:

- **Latest run per suite** (the default) — only each suite's most recent run in the window. Totals are deliberately smaller.
- **All runs in window** — unique tests across every run in the window. Totals match **Coverage**.

If the summary "does not match" another page, it is almost always the aggregation or the window; both are shown on the page. **Views** saves the window, release, suite and aggregation as a named view.

## Summary report files

The Summary report's **⋯** menu offers **Export PDF**, **Export Excel**, **Export PDF in background**, **Export Excel in background**, and **Analysis report (1d)** / **Analysis report (7d)**.

- A small report downloads at once. A large one, or one you send in the background, is prepared as a job, so you can keep working.
- **Background exports** lists your jobs: Queued, Generating…, Ready or Failed. It updates by itself while a job runs, and a message with **Download** appears when the file is ready. **Retry** sends a failed job again.
- A finished file stays downloadable for **7 days**, then it is removed.
- Your access is checked again when the file is generated and when it is downloaded: losing project access stops both.
- Every export is recorded in the audit log with its scope and size.

The **analysis report** is one self-contained HTML file (`testlookup-report-<project>-<date>.html`) that works offline: an executive summary, the runs, new and recurring failures, flaky tests and quarantines, the slowest tests, the latest release-gate verdict, linked defects and failures by owning team, for the last day or the last 7 days. The same file can be attached to a daily or weekly email digest (**Admin → Integrations → Digests & views**).

To export one chart instead, use its **Export** menu: see [Charts and visual analysis](/docs/charts).

## Value metrics

**Reports → Value** (`/value-metrics`, titled **Value Metrics**) answers "what is this saving us": an estimate of **engineer-hours saved in the last 30 days**, its full-time equivalent, a monthly trend, and the counters behind it (**Defects grouped**, **Duplicates avoided**, **Flaky tests found**, **Releases blocked**, **AI reports**). The headline is always the last 30 days; the window picker changes the counters, not the headline. **How is this calculated?** opens the full method.

### How the hours are estimated

Hours saved is the sum of three parts, each *count × minutes ÷ 60*:

| Part | Count | Default minutes |
|---|---|---|
| **Triage** | Failing executions absorbed into failure clusters of size 2 or more | 20 per failure |
| **Quarantine** | Runs whose every failing test was in an active quarantine at the time (a proxy for "runs not blocked") | 30 per run |
| **Dedup** | Duplicate failures absorbed into an existing cluster (cluster size minus one) | 15 per duplicate |

The full-time equivalent divides the hours by 173.2 working hours a month. AI analyses are shown for context but not multiplied into any part, so a failure is not counted twice.

Read it honestly:

- **Cluster instances, not distinct defects.** Each recurrence of the same underlying problem counts, because each would have interrupted someone.
- **The quarantine part is a proxy.** Quarantines released later stop counting their past windows — a deliberate undercount.
- The defaults come from published research (a full failure investigation costs hours; a context switch costs 15–25 minutes) and sit at the cautious end.

**Model assumptions** (QA leads and administrators, one project selected) lets you change the three minute values for your team (each above 0 and at most 480) and **Save assumptions**. Everyone in the project sees the values in use, marked **Customized** or **Defaults**.

### When the headline is hidden

The page shows "Not enough data yet to estimate engineering hours saved." with the reason, instead of a number, until the project has at least **14 days** between its first and last run **and** a non-zero estimate for the last 30 days. Digests leave out the hours-saved line under the same conditions.

## Sharing and retention

**⋯ → Share report** on the release gate creates a read-only link to that decision report and copies it to your clipboard. Anyone with the link can open it without signing in, as a web page or a PDF, until it expires (7 days by default; up to 30 through the API) or is revoked. Every access is recorded in the audit log. If human review of AI reports is mandatory, an unreviewed report cannot be shared.

How long runs, artifacts and audit records are kept is an administrative setting; see [Settings and administration](/docs/administration#retention-and-purge).

> **Warning.** A shared report carries whatever was in it, including error text and stack traces from your tests. Review before sharing outside the team. See [Security and privacy](/docs/security).
