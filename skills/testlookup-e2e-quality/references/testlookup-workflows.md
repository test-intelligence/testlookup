# TestLookup test entry points

Confirm entry points in the tested revision. Start with `docs/operations/testing.md`, `frontend/package.json`, the Playwright configs, `e2e-runner/README.md`, and the relevant workflow under `.github/workflows/`. Older refs can lack the release runner or use different tests and credentials.

| Lane | Repository entry point | Evidence and limits |
| --- | --- | --- |
| Browser CI | From `frontend`, `npm run test:e2e:ci -- --list` to collect and `npm run test:e2e:ci -- <spec>` for a focused run. `playwright.ci.config.ts` selects `tests/ci-e2e`. `.github/workflows/ci.yml` runs the browser lane. | Hermetic UI behavior for stubbed endpoints. Verify mocks and assertions before claiming coverage of a product contract. Collection proves discovery only. |
| Mixed browser E2E | `frontend/tests/e2e/COVERAGE.md`, `playwright.config.ts`, and `npm run test:e2e -- <spec>`. Review `global-setup.ts`, auth helpers and each spec. | The runner can use a deployed app, real login helpers and API interceptions in the same suite. Default setup may try dev-login and write auth state. Use only an appropriate isolated target and classify each spec by what it actually exercises. |
| Route and action sweeps | `playwright.sweep.config.ts` and `frontend/tests/sweeps/`, where present. Read the named actions and fixture setup before selecting a sweep. | Live breadth by route and role. Missing fixtures can skip the entire sweep. A rendered page or successful HTTP response provides initial smoke evidence. |
| Functional release | `e2e-runner/release_campaign.py` coordinates regression and upgrade evidence. See `e2e-runner/README.md` and `upgrade_README.md` for runtime setup. `frontend/tests/release/` covers browser paths and `e2e-runner/live/` covers API, CLI, SDK, and MCP paths. | A verified `release-manifest.json` selects digest-qualified images. The disposable target supports write journeys and deterministic external substitutes. For isolated smoke or focused local diagnosis, use the documented `e2e-runner/launch.py` path. |
| Nightly and stable release | `release-e2e-nightly.yml` selects the full tier. `release-e2e.yml` verifies a source SHA and publishes `release-functional-evidence`. `release.yml` uses functional verification before promotion. Read the workflow on the chosen ref. | Read `summary.md`, `results.json` and `release-junit.xml`. Match `observed_build.revision` and `manifest_hash` to the intended artifact. The workflow requires an actual `GO` attestation for promotion. Smoke acceptance alone leaves the release gate unsatisfied. |
| Shared deployment | Use the release runner's approved shared target mode as documented in `e2e-runner/README.md`. | Read-only smoke and role identity. Verify configured identities for VIEWER, TESTER, QA_ENGINEER, QA_LEAD and ADMIN as required by the runner. Load scoped credentials from the configured secret mechanism. Missing identities, reachability or image proof leave the affected checks unverified. |

## Verify wiring and scope

- For a release obligation, use a stable `TL-*` ID and matching catalogue row, runnable test, title or JUnit name recognized by `e2e-runner/run.py`, and recorded outcome. Check format and role expansions, tier eligibility and upgrade merge rules. Use the runner's expected inventory for the run denominator.
- Match the test layer to the risk. For data processing and worker behavior, compare producer facts with receipt completion, durable records and surfaced results. For UI behavior against a stub, check the guarded request or UI state and use a separate integration or live test for backend behavior. For AI, use deterministic fixtures for workflow assertions and record the provider mode.
- Prioritize changed contracts that can affect a release decision or lose test evidence. Useful comparisons include one run and failure across the UI, reports, CLI and MCP, pass-rate denominators with skipped-only inputs, project and release scope after a switch, and reviewed versus pending evidence in exported reports. Derive the expected IDs, counts and decisions from the current contract and fixtures.
- Verify release policy against `e2e-runner/policy.py` and the promotion workflow. Preserve first-attempt status. A pass on retry remains flaky. Missing tests or prerequisites, unexpected skips, a stale manifest, and failed upgrade evidence must remain visible. Record approved, unexpired waivers as the policy permits and preserve the runner's actual verdict.
- For Podman or Kubernetes, establish the exact candidate and required previous build, topology, migrations, dependencies and test principals. Use fresh isolated resources and output directories. Verify cleanup of resources created for that run. Shared/prod-like diagnostics use authorized read-only probes with bounded scope.
- Keep raw reports, Playwright traces, browser state and private logs in the approved evidence location. Publish only sanitized summaries. Use `e2e-runner/history.py` for repeat runs of one target, tier and candidate manifest. Use the coverage ledger for trends across candidates.
